## Findings from this pass (test-coverage gaps against TRD §9 v2, not code defects)

None of the following are rendering/behavior defects — the underlying code was independently traced correct (F1a/F1b/F2, confirmed again in this pass, see Evidence). These are gaps between what TRD §9 v2 requires the test suite to assert and what is actually committed, found by checking each v2-amended row against the real test files rather than trusting the round-9 review's "APPROVE WITH MINORS, unexecuted full suite" summary.

- **F-QA1 (row 2e).** `SearchQueryTests.performanceAtCeiling` queries `"keyword3-1000"` against the synthetic 2,000-place index — that keyword pattern (`"keyword\(k)-\(i)"`, unique per place `i`) matches **exactly 1** place, and the test asserts no result count at all. TRD §9 v2 row 2(d) was rewritten specifically to require "the timed call must return a stated non-zero result count (a query chosen to match ≥ 100 of the 2,000 synthetic rows), asserted before the timing is read... a matcher that returns `[]` instantly satisfies a bare time bound, so the bound alone proves nothing." As shipped, this test would pass identically if `SearchQuery.run` always returned `[]`. Non-blocking for this verdict (the matcher's correctness is independently proven by every other `SearchQueryTests`/`SearchShippedSeedTests` case), but it is the same L-009 failure shape the v2 amendment exists to close, surviving in the one row written to prevent it.
- **F-QA2 (rows 3b/3c).** No committed test runs `SearchQuery.run` against the **real shipped seed** (`places-tel-aviv.json`/`hoods-tel-aviv.json`) with an active chip filter. `CategoryFilterTests` covers only the pure `CategoryFilter` enum; `SearchQueryTests.chipNarrowsPlacesOnlyNotHoods` uses a synthetic 2-place/1-hood fixture with different names, not the TRD's literal `"b"` query. Verified by hand this pass (§3.4 below) that TRD §9 v2's own exact arrays for row 3(c) — `run("b", .only(.eatDrink))` → `["Bavli", "Anna Loulou Bar", "HaMakolet", "Suzanne Restaurant"]`, `run("b", .all)` adds `"Carmel Market Spice Corner"` — are correct against the real 9-place/24-Hood seed, matching the architect's own D14 trace. The requirement holds; nothing regresses it automatically.
- **F-QA3 (row 4a-cityWide-count).** No integration test constructs the real 24-Hood set through `MapScreen` (or an equivalent harness) and asserts "exactly 1 of 24 undimmed" + "`PlaceLayer` count == 0 at `.cityWide`" together, which is TRD §9 v2's literal row 4(a) condition. The mechanism is proven at the unit level (`HoodLayerFillDimTests`, `HeatPaletteTests`, `SearchDimTests`) and the rendered, composed result is confirmed live this pass (see Evidence) — this is exactly the split the TRD's own Layer column specifies ("unit + UI test + manual (visual dim)"), so the manual pass is not a workaround, it is the specified check. But there is currently no **automated** regression guard at the composed/rendered layer — a future change that re-breaks F1a or F1b in combination (rather than in the isolated `HoodLayer`/`SearchDim` units already covered) would not be caught by CI, only by another manual pass.
- **F-QA4 (row 8c-ii), already known.** Confirmed independently: `SearchRowGrowthGuardTests` has no positive-control assertion that `CategoryChip`'s `Text` carries `.fixedSize`, unlike the matching check for `SearchResultRow`. Already flagged non-blocking by `ios-code-reviewer` (2026-08-03); not re-raised as new.

None of F-QA1–F-QA4 block this verdict on their own — each is a coverage gap around an already-correct behavior, independently re-derived from source and/or live rendering, not a defect in the shipped feature.

- **F-QA5 (row 4a-fill/4a-live/4b/4f), new this pass, the reason the overall verdict is BLOCKED rather than PASS WITH MINORS.** Between round 9's review and this QA run, an unrelated concurrent ticket — **PAS-49** (`passenger-code c1b8bc3` "HoodLayer polygons render border-only, no interior fill", further fixed in `5e1f72f`) — landed on `main` and rewrote `HoodLayer.body` to draw `.foregroundStyle(.clear)` unconditionally in every `effectiveStroke` branch. `HoodLayer.fillColor` — the exact property TRD §9 v2 row 4(a) names, and the only property `HoodLayerFillDimTests` asserts against — is no longer read by `body` anywhere. It still computes correctly (`dimOpacity` still multiplies in), so the existing test suite is still green, but it is now a **dead-assertion suite**: a suite-green run proves nothing about what the app renders. `5e1f72f`'s own commit message discloses this directly ("`HoodLayerFillDimTests` still asserts on `fillColor`, which body no longer renders — a dead-assertion suite that should be retargeted at `borderColor`") but does not fix it, and fixing `HoodLayer`'s test coverage is not PAS-49's own scope either — it fell into the gap between two tickets. The channel that actually renders now, `borderColor`, **has zero test coverage anywhere** (`grep -rn borderColor PassengerTests/ PassengerUITests/` → 0 hits, this pass). Direct code read of `borderColor` (`HoodLayer.swift:165-169`) shows it does correctly carry `* dimOpacity` in both its banded and no-band branches, so the underlying dim behavior is very likely still functionally present — just via a thin stroke line instead of an area fill, a materially weaker visual channel than what F1a was built to fix, and with no automated test protecting it either way. This is the same L-009 failure shape as T-046 and T-053 (a check that's true for the wrong reason / at the wrong layer), recurring a third time on this exact requirement, caused entirely by a change outside this ticket's own diff. **Live confirmation attempted, partially completed, then BLOCKED** — see Evidence below; the one clean live screenshot obtained shows thin coloured Hood outlines (consistent with `borderColor` rendering, not an area fill), but a controlled before/after search-dim comparison was not completed this session.
