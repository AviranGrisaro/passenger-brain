1. Context

Read the PRD first; nothing here restates it. This document decides the five things it left open and pins the one contract two other PRDs are waiting on.

What this task is, architecturally: not a feature. It is a build-time data pipeline plus three additive columns. No runtime code path changes shape — the client reads the same bundled file it reads today, the same table it queries today. What changes is that the file and the table stop containing rectangles, gain three fields, and start being generated from a checked-in source under a validator that can fail the build.

2. Architecture

2.1 The pipeline, inverted

Today (T-031 B3):

hand-written SQL seed → [Postgres] → export_hoods_geojson.py → bundle
                                     ↑ needs DATABASE_URL (Aviran-gated)

The DB is the source of truth, the migration is the authoring surface, and the only path from source to client runs through a live database. Two consequences: the bundle can only be regenerated by someone with credentials, and the migration — the actual authored artifact — is hand-edited SQL with coordinates inline, where a geometry review means reading jsonb literals in a diff.

This TRD:

database/data/hoods-tel-aviv.source.json     ← the only authored file, git-tracked
                 │
                 ▼
        build_hoods.py  ── validate (§5.2) ──► fail loudly, write nothing
                 │
        ┌────────┴────────┐
        ▼                 ▼
migrations/NNN_hoods_    passenger-code/…/Resources/
tel_aviv_data.sql        hoods-tel-aviv.json
   (DB seed)                (iOS bundle)

One authored source, one generator run, two generated artifacts, no database access required. Both artifacts are committed. ios-developer, developer, data-engineer, qa and ios-code-reviewer can all run the generator and reproduce both files byte-for-byte from the source.

This is what PRD req 6 actually asks for. The PRD describes it as flowing through "the existing export_hoods_geojson.py" — that script cannot do it, because it runs in the wrong direction and starts from a resource nobody in the pipeline can read.

export_hoods_geojson.py is not deleted and not replaced in place. It is repurposed as the drift check (§5.3): given credentials, it exports the live table and diffs against the committed bundle. A non-empty diff means someone edited the DB out of band. That is a genuinely useful second-line check, it is the one job the DB→bundle direction is right for, and it honours the standing no-rm rule without leaving a misleading tool in scripts/.

2.2 Boundaries — who is allowed to know what

  • database/data/ holds authored data and nothing else. No SQL, no code, no derived values. A human (or an OSM/municipal extraction run by data-engineer) writes it; everything downstream is generated.
  • database/scripts/validate_dataset.py is the only place polygon math lives in the offline authoring pipeline. Ring validation, non-overlap, area-weighted centroid, and point-in-polygon resolution. It is called by this task's exporter and by T-042's build — see §4.4, which adopts places-dataset/TRD.md §4.1's C-HOOD-1 clause 4 and its file name verbatim. Both consumers are stdlib Python running offline over checked-in source files, with no database access by design (§2.1) — which is exactly what makes one shared file possible.
  • T-043 is not a third consumer of this file, and an earlier draft of this TRD said it was. Correcting that. live-events-pipeline needs the same predicate at a fundamentally different seam: a plpgsql hood_for_point() running live inside Postgres, against the hoods table (not the authored file), attributing externally-sourced events at ingest inside a Deno Edge Function's SQL path. No practical bridge exists in either direction — a cron-triggered ingest path shelling out to a Python subprocess per event is proposed by no TRD and does not belong in a hot path, and pointing this offline validator at a live database reintroduces the exact Aviran-gated DATABASE_URL dependency §2.1 inverted the whole pipeline to escape. Two implementations of the same even-odd ray cast, both necessary. What is shared is not code:
  • One algorithm spec, stated identically in all three TRDs — closed single-ring WGS84 [[lng,lat],…], even-odd ray cast, bbox prefilter, on-boundary → false.
  • One checked-in fixture file of point→expected-hood_id cases, asserted against both implementations (§9 B1; places-dataset/TRD.md §9 B2a; live-events-pipeline/TRD.md §9 A3), so a boundary-case fix in one language cannot silently stay wrong in the other.

Resolved at trd-review by data-engineer and code-reviewer across all three tasks. The failure this prevents is specific: a place and a live event at the identical coordinate attributing to different Hoods. - database/migrations/ is output, for the data migration. NNN_hoods_tel_aviv_data.sql is generated and must never be hand-edited. The schema migration (§3.1) is hand-written and stable — it is applied once and never regenerated. - Hoods/ on the client stays as T-031 built it (map-hoods-heat/TRD.md §2.2): no network, no density. It gains three stored attributes and one precomputed centroid. It gains no behaviour.

2.3 Third-party dependencies: none added

An earlier draft of this TRD specced Shapely for the non-overlap check. places-dataset/TRD.md §6 rejects it by name — a C/GEOS dependency and a build story on a project whose only existing script is stdlib Python — and that rejection is adopted here. One shared validator (§4.4) cannot have two dependency stories, and the reasons for stdlib are the same on both sides.

Candidate Call
Shapely / GEOS Rejected, per places-dataset/TRD.md §6. A build-time C dependency for two predicates that are writable in stdlib.
PostGIS / ST_Overlaps Rejected. It puts the invariant behind the credential wall this TRD exists to get out from behind, and T-031 already declined to enable PostGIS (map-hoods-heat/TRD.md §2.3). Nothing here needs a server-side spatial query.
Stdlib Python geometry Adopted. No new dependency in either repo.

One correction to C-HOOD-1 clause 4's stated rationale, which data-engineer needs before estimating B1. Clause 4 says the two invariants "are the same ray-cast over the same rings." That is exactly true of T-042's containment check and not true of this task's non-overlap check. Overlap between two polygons is not a ray-cast, and the file is shared for the right reason — one owner for all polygon math, one set of ring conventions — not because the two checks are the same code. Clause 4's conclusion holds; its stated reason under-describes the work. Concretely, non-overlap is three stdlib predicates, ~150 lines rather than ~30:

  1. point_strictly_inside(p, ring) — even-odd ray cast, with on-boundary returning False. Shared with T-042's containment check, which is the part clause 4 is right about.
  2. segments_properly_cross(a1,a2,b1,b2) — a transversal crossing only: strict orientation sign changes on both segments. Collinear overlap and endpoint contact deliberately return False.
  3. polygons_overlap(A, B) = any vertex of A strictly inside B, or any vertex of B strictly inside A, or any edge pair properly crossing.

That composition is what makes shared boundaries legal. Adjacent neighbourhoods share edges by construction; a naive segment-intersection test flags every shared edge and the dataset could never pass. Proper-crossing excludes collinear and endpoint contact, and strict-interior excludes on-boundary vertices, so two Hoods sharing a full edge report clean while two overlapping by a sliver report a violation (their edges must cross transversally somewhere). It is also complete for containment: if A ⊂ B with no crossing at all, every vertex of A is strictly inside B and predicate 1 catches it.

What is genuinely lost with Shapely gone, stated rather than glossed: an exact overlap area, so V6 has no ε tolerance knob — a violation is a violation. That is the behaviour §9's first risk row argues for anyway (the fix for source imprecision is vertex snapping, not a widened tolerance), so it costs nothing here. And exact union geometry, so V7's coverage-gap check becomes sampled rather than exact — see §5.2 V7 and §8 D9. The two are not equivalent risks and are not treated as one: overlap is approximated by nothing, because HoodHitTester's correctness rests on it; coverage is a legibility judgement where a 50 m sampling grid resolves gaps an order of magnitude below the threshold that matters.

Area-weighted centroid (§8 D5) needs no library either — the shoelace centroid is ~15 stdlib lines, and self-intersection detection (V3) is predicate 2 applied to a ring against itself.

3. Data model

3.1 Backend — schema, migration 003_hood_attributes.sql

alter table public.hoods add column if not exists blurb                      text;
alter table public.hoods add column if not exists is_tourist_trap            boolean;
alter table public.hoods add column if not exists designated_for_progression boolean not null default false;

Three columns, no index, no RLS change. hoods already has enable row level security and one public select policy from 001 A2; new columns inherit it, and there is still no write policy anywhere — PRD req 5's last bullet is satisfied by not changing anything, which is the correct amount of work.

Four decisions inside those three lines:

  • is_tourist_trap is nullable with no default. Three storage states — null not yet rated, false not flagged, true flagged — because tourist-trap-flag reqs 4 and 7 need all three: the map renders null and false identically, VoiceOver does not. A not null default false here would collapse the distinction at the schema level and make req 7 unimplementable, which is the kind of thing that is free to get right now and a migration plus a data audit to fix later.
  • designated_for_progression is not null default false. The opposite call, for the opposite reason: passport req 4 has no "unknown" state — a Hood is either counted toward Local or it is not — and null would be a third state nothing renders. The default makes every existing row correct without a backfill.
  • blurb is nullable and null means "not curated." Empty string is not a permitted value; hood-place-detail req 2 forbids placeholder copy, and null is the only representation of its absence. The validator rejects "" and whitespace-only at authoring time (§5.2 V8) rather than relying on the client to normalise it — though T-033's client does normalise it too (hood-place-detail/TRD.md §4.3), and both layers doing it is correct.
  • Nothing else is added. No source/provenance column, no centroid column, no area. Provenance lives in the authored source file (§3.2) where it is needed for re-derivation and licence attribution; centroid is derived and lives in the generated bundle (§8 D5). A column exists in this schema only if something reads it over the wire.

This migration collides with T-033's TRD and the collision is resolved here — see §8 D7. hood-place-detail/TRD.md §3.1 declares a migration 003_places_and_hood_blurb.sql that also adds hoods.blurb. Neither 003 exists on disk. hoods.blurb is this PRD's req 4, product's sweep assigned it here, and T-040 is first in the dependency chain — so it lands here and T-033's A1 drops it.

Field Type Required Rule

lng before lat is the format 001 and the existing script already committed to, and the single most common way a geospatial dataset ships silently broken. V4 (§5.2) catches a swapped pair by range, which works because Tel Aviv's latitude (~32) is inside longitude's valid range but its longitude (~34.8) is also inside latitude's — so range alone is not sufficient. V5 adds a bounding-box check against Tel Aviv specifically, which is.

on conflict (id) do update, not do nothing. This is a correction, not a style preference. Migration 001 A3 writes on conflict (id) do nothing and its own header comment claims the real export "supersedes these rows by id (upsert-shaped, see below)" — the comment and the SQL disagree, and the SQL wins. Under do nothing, the three ids the real dataset shares with the placeholder set (florentin, neve-tzedek, lev-hair, and possibly old-north/jaffa) would keep their placeholder rectangle geometry after the "real" seed applied, and 001's rectangles overlap the real polygons of their neighbours. The swap would ship a dataset that fails the very invariant this task exists to enforce, and it would look like it worked.

The delete is what removes placeholder ids the real dataset drops. Scoped to city = 'tel-aviv' so it can never touch a future second city. It cascades into hood_density via 001's on delete cascade, which is correct — the generator (002) rewrites 13 rolling buckets per Hood hourly and regenerates them within the hour. It must not cascade into places — see §4.4 and §8 D6.

Migration numbering is an argument, not a guess. build_hoods.py --migration-number 006 writes 006_hoods_tel_aviv_data.sql. The generator never scans the directory and picks the next free number: several TRDs are in flight against this same directory and a race there produces two files with the same number and no error. chief-of-staff sequences; the number is passed in.

This task needs two migration files, and only the first is 003. The settled workspace sequence is 003 = this task's schema migration (§3.1, 003_hood_attributes.sql), 004 = places-dataset (004_places.sql, T-042), 005 = live-events-pipeline (T-043). This task's generated data seed is a separate file and an earlier draft of this section numbered it 004, which collides with T-042's already-claimed 004_places.sql. It is renumbered up to 006_hoods_tel_aviv_data.sql. Pure renumber — no design change, and 003_hood_attributes.sql is unaffected and stays where it is. Landing the data seed after T-042's places table is also the harmless order: 004 only needs hoods to exist, which 001 already provides, and §3.3's delete is city-scoped and blocked from touching places by on delete restrict (§4.4, §8 D6) regardless of which file lands first.

Re-issue rule, using the machinery that already exists. database/README.md tracks an Applied? column per migration. While a data migration is not applied, correcting the source regenerates that same file in place. Once it is applied, database/README.md's rule holds absolutely — never edited, never renumbered — and the next revision is a new number. Since 001 and 002 are both still blocked-on-aviran and unapplied, the practical near-term reality is regenerate-in-place.

3.4 Polygon format — single ring, enforced (PRD open question 1, resolved)

V1 stays single-ring, and the validator rejects multi-ring input loudly rather than flattening it.

Single-ring is not a preference inherited from 001; it is load-bearing in four shipped places: hoods.polygon is a bare jsonb ring (001); HoodCatalog.CatalogFile.Entry.polygon decodes [[Double]], exactly two levels; HoodHitTester.contains ray-casts one ring with a single wraparound; MapPolygon(coordinates:) takes one coordinate array. Supporting a hole or a detached exclave is a bundle schema bump, a decoder change, a hit-tester change (even-odd across rings), a renderer change (N polygons per Hood), and a DB shape change — for a case that may never arise in Tel Aviv.

Authoring rule instead of a schema change. If a real municipal boundary has a hole or a detached part:

  1. Simplify to the single outer ring at authoring time, if the excluded area is not itself a Hood; or
  2. split it into two Hoods with distinct slugs, if the parts are genuinely distinct places.

Both are data decisions with a human in the loop, which is right for a dataset with dozens of rows.

The escalation trigger is named, so nobody quietly picks option 3. If data-engineer finds a Tel Aviv Hood that neither rule can honestly represent — a real donut, or an exclave that residents call one place — that comes back to architect as a scope change, not a workaround. The validator makes this unavoidable: V2 rejects a nested array, so the only way past it is to change the spec.

4.2 Ring canonical form — closed on the wire, open in memory

Layer Form Why
Source file, hoods.polygon, bundle JSON Closed (ring[0] == ring[-1]) One canonical wire form. Matches 001's seed, GeoJSON convention, and what export_hoods_geojson.py:92 already enforces. Removes the drift named in §1.
Hood.ring in memory ([MKMapPoint]) Open — HoodCatalog drops the duplicated final point at decode This is what today's shipped code already assumes and what the math wants.

The in-memory choice is not cosmetic. HoodCatalog.centroid(of:) is an average of vertices, so a duplicated closing point silently double-weights one corner; HoodHitTester.distanceToEdge would evaluate a zero-length segment (its lengthSquared > 0 guard handles it correctly, but it is work for nothing); MapPolygon closes the ring itself. Dropping the duplicate at the boundary keeps all three correct with one line.

HoodCatalog.load() gains this and the three attributes. It must accept both — an open ring (a stale v1 bundle) and a closed one — by dropping a trailing duplicate only when present. This is boundary validation, not defensive programming: the two forms are both in the repo right now.

4.3 HoodCatalog / Hood — the iOS-side change

struct Hood: Identifiable, Sendable {
    let id: String
    let name: String
    let ring: [MKMapPoint]
    let boundingRect: MKMapRect
    let centroid: CLLocationCoordinate2D   // now read from the bundle, not averaged (§8 D5)
    let blurb: String?                     // nil == not curated, never a placeholder
    let isTouristTrap: Bool?               // nil == not yet rated (three states)
    let designatedForProgression: Bool
}

Hashable stays id-only (already the case, and now more necessary — none of the three new fields participate in identity). Hood stays Sendable — three value types, no new conformance question.

Consumers, so trd-review can check nothing is being pre-built: T-033 reads blurb, T-035 reads isTouristTrap, T-037 reads designatedForProgression. All three are downstream tasks; this task only stores and exposes the fields. It renders nothing, adds no view, and adds no behaviour to Hoods/.

Decode rules (boundary validation): centroid optional — fall back to the computed average if absent, so a stale bundle still loads; blurb optional, and ""/whitespace normalised to nil; isTouristTrap optional; designatedForProgression defaults false if absent. schemaVersion is read and required to be >= 1; an unknown higher version is not rejected, because a v1 decoder facing a v2 file already ignores unknown keys correctly and a hard version gate would only turn a working case into a crash.

4.4 C-HOOD-1 — the places ↔ hoods contract

Authored in places-dataset/TRD.md §4.1 and quoted here verbatim rather than restated, per that section's own instruction that both TRDs must state it in the same terms so they cannot drift. This TRD adopts all four clauses without amendment:

  1. Referential. places.hood_id is a foreign key to hoods.id, on delete restrict. Free text is not acceptable (req 1). restrict, not cascade — see §3.2.
  2. Geometric. For every place, ray-casting (longitude, latitude) against the single-ring WGS84 [[lng,lat], …] polygons (001's committed format, ratified by export_hoods_geojson.py) yields exactly one containing Hood, and places.hood_id equals that Hood's id. Zero containing Hoods → fail, never ship unattributed (req 1). Two or more → fail, and the failure is also a live counter-example to hood-dataset req 2's non-overlap invariant, so it is reported against both datasets.
  3. Enforcement site. The geometric clause is enforced by validate_dataset.py, not by Postgres. There is no PostGIS on this project and hoods.polygon is jsonb, not geometry; a DB-level containment constraint would mean adding a spatial extension for one authoring-time check. The FK gives referential integrity; the validator gives geometric correctness. A place is never written to the DB or the export without the validator passing.
  4. Single implementation, shared. database/scripts/validate_dataset.py owns both invariants — T-040's non-overlap check and this task's containment check — because they are the same ray-cast over the same rings, and two implementations would disagree eventually. T-040's build calls it; T-042's build calls it. Whoever builds it first writes it; the second task consumes it.

This TRD's obligations under those clauses:

  • Clause 1 is satisfied by a correction, not by new work here. hood-place-detail/TRD.md §3.1 currently declares places.hood_id … on delete cascade. With §3.3's prune, dropping a Hood in a geometry revision would silently delete the curated places inside it. T-042's §2.1 already resolves ownership of the places table away from T-033; the on-delete change travels with it. §8 D6.
  • Clause 2's "exactly one" is this task's invariant, not T-042's. Containment yields exactly one Hood because V6 (§5.2) has run and passed. T-042 and T-043 are correct because this task's validator runs, not because they check anything themselves. That is the dependency chain in one sentence.
  • Clause 4's file name and ownership are adopted verbatim; its stated rationale under-describes the non-overlap half, which §2.3 corrects without changing the conclusion. hoodgeom.py, named in an earlier draft of this TRD, does not exist — everything is in validate_dataset.py.
  • T-043 (live-events-pipeline) req 3 — "hood_id resolved from the event's coordinates at ingest," "an event in no Hood is not ingested" — is clause 2's same predicate, but not clause 4's shared file: T-043 implements it in plpgsql against the live table (§2.2). Held to the same algorithm spec and the same fixture, including on-boundary → no Hood, so an event on a shared edge resolves the same way a place on that edge does. Its FK into hoods follows clause 1's restrict rule (§9).

4.5 build_hoods.py — CLI contract

python3 build_hoods.py
    [--source   database/data/hoods-tel-aviv.source.json]
    [--sql-out  database/migrations/NNN_hoods_tel_aviv_data.sql]
    [--json-out passenger-code/Passenger/Resources/hoods-tel-aviv.json]
     --migration-number NNN
    [--check]        # validate only; write nothing; non-zero exit on any violation

Exit 0 clean, 1 on any violation with every violation printed (not just the first — a dataset with six overlaps should take one run to find all six, not six runs). No network, no DATABASE_URL, no credentials. Deterministic: same source in, byte-identical artifacts out, so a reviewer can regenerate and git diff --exit-code to prove the committed artifacts match the committed source.

5. Flow

5.1 Authoring → shipped

data-engineer sources geometry (OSM / municipal / manual — method open)
   └─► writes/updates database/data/hoods-tel-aviv.source.json   ← the only hand-edited file
        └─► build_hoods.py --migration-number NNN
             ├─ V1…V9 validate  ─── any violation ──► print all, exit 1, WRITE NOTHING
             └─ clean
                 ├─► migrations/NNN_hoods_tel_aviv_data.sql   (passenger-brain commit)
                 └─► Resources/hoods-tel-aviv.json            (passenger-code commit)
                      └─► HoodCatalogTests re-asserts non-overlap on the shipped bundle
                           └─► migration applied (Aviran-gated) ──► export_hoods_geojson.py --check

Two repos, two commits, one source. The cross-repo write is not new — export_hoods_geojson.py's DEFAULT_OUT already resolves parents[3] / passenger-code / ….

5.2 Validation — the fail-loudly step (PRD req 2, open question 2, resolved)

Runs inside the generator, before either artifact is opened for writing. A dataset that violates any of these does not produce a partial artifact.

# Check Failure
V1 Slug format, uniqueness, non-empty name error
V2 polygon is exactly [[lng, lat], …] — a third nesting level is an error, not a thing to unwrap (§3.4) error
V3 Ring is closed, ≥4 points, ≥3 distinct points, and not self-intersecting (§2.3's proper-crossing predicate applied to the ring against itself) error
V4 Every coordinate in range, lng first error
V5 Every coordinate inside a generous Tel Aviv-Yafo bounding box (≈34.72–34.86 E, 32.01–32.14 N, deliberately loose) error — PRD req 1's "no Hood for any other city", and the only reliable swapped-lat/lng catch (§3.2)
V6 Non-overlap: polygons_overlap(a, b) for every pair, bbox-prefiltered — §2.3's three stdlib predicates. Touching boundaries are legal; overlapping interiors are not. No tolerance knob, by design. error, and this is the check the whole task exists for
V7 Interior coverage gaps, sampled: a 50 m grid over the §V5 bounding box, cells whose centre is in no Hood, contiguous uncovered cells clustered; a cluster fully enclosed by covered cells with area > 40,000 m² is an error, > 5,000 m² a warning. Clusters touching the sampled region's edge are exterior, not interior — skipped (§8 D9) error / warn — PRD req 1's "no unnamed interior hole large enough to read as a rendering bug", made falsifiable
V8 blurb is null or non-blank; "" and whitespace-only rejected error
V9 isTouristTrap ∈ {true,false,null}; designatedForProgression ∈ {true,false}, never null; provenance.source ∈ the enum error

Slug-preservation check (PRD req 3's third bullet), a warning not an error: the generator compares the source's ids against 001's five seeded slugs and warns for each one that disappears. It is a warning because dropping old-north may be a legitimate authoring decision, and an error would make a correct dataset unshippable. It prints, so nobody drops one by accident.

V6 is the reason this task exists. HoodHitTester.hood(at:tolerance:) takes hoods.first(where: { bbox.contains && contains(ring) }) — first match wins, file order decides, and it comments "Hoods don't overlap (PRD req 3), so at most one hit is possible here." That comment is currently an unchecked assumption that happens to hold because the four shipped rectangles are disjoint. The moment real adjacent polygons land it becomes a live correctness claim with nothing behind it. V6 is what makes the comment true.

5.3 Two more places the invariant is checked

  • HoodCatalogTests (iOS), against the shipped bundle. A pure-Swift pairwise bbox-overlap prefilter plus segment-intersection and vertex-containment test over the decoded rings, asserting no two Hoods overlap and no vertex of one lies strictly inside another — the same three predicates as §2.3, ported. It is a tripwire against the artifact that actually ships, not a second authority. Its job is to catch a hand-edited bundle, which is the one path around the generator. It also asserts every ring decodes, and that ids are unique.
  • export_hoods_geojson.py --check (post-apply). Exports the live table, diffs against the committed bundle, non-zero on drift. The only check that can catch a manual update run against the production database.

5.4 What happens when geometry is corrected later

  1. Edit the source. Ids do not change (PRD req 3).
  2. Re-run the generator — V1…V9 re-run over the whole dataset, so a correction cannot introduce an overlap somewhere else and go unnoticed.
  3. If the previous data migration is unapplied, it regenerates in place; if applied, --migration-number gets the next number (§3.3).
  4. Places and events re-resolve. T-042's and T-043's validators re-run resolve_hood against the new source; anything that now falls in a different Hood or no Hood is a violation there. The on delete restrict FK (§4.4) is the backstop if step 4 is skipped.
  5. Been-place re-attribution (PRD open question 3) is genuinely not answered here. Been state is device-local (T-033 §3.5, T-036), so no backend step can migrate it, and a boundary correction can move a user's Been place into a different Hood and change their Passport progress. Naming it: it is passport's own open question, it is not solvable by this pipeline, and it becomes real only after launch. Flagged in §10, not designed around.

  • None added (§2.3). Stdlib Python on the backend side, no SPM package on the client side. map-hoods-heat/TRD.md §2.3's "no third-party packages until a TRD justifies one" is not being invoked, and places-dataset/TRD.md §6's stdlib-only posture is matched exactly — the two tasks share one file and cannot have two dependency stories.

7. Rollout & migration

  • No feature flag. This is a data swap on a screen that already renders. Its off-state is the placeholder rectangles, which is worse than its on-state in every dimension. A flag here would be machinery to preserve a known-wrong dataset.
  • Order is strict and both halves are independently shippable. 003 (schema) → NNN (data) on the backend; the bundle swap on iOS. The two do not have to land together: the iOS build reads the bundle and never the new columns over the wire in this task, so ios-developer can ship real geometry while 003 sits blocked-on-aviran — the same decoupling that let T-031 ship at all.
  • Applying is Aviran-gated. database/README.md. developer writes and hands off; no agent applies. 003 is additive and if not exists-guarded, so it is safe to apply before or after 001/002 — but it depends on hoods existing, so 001 first.
  • Backward compatibility. 003 is three add column if not exists — no rewrite of an applied migration, no data loss, and every existing row is valid the moment it applies (blurb/is_tourist_trap null, designated_for_progression false). schemaVersion 2 is decode-compatible in both directions (§4.3).
  • 002's synthetic generator needs nothing. It joins hoods by id and is indifferent to the new columns. It does re-key onto whatever Hood set survives the prune, within the hour.
  • The placeholder era ends explicitly. database/README.md's status table gets a row for 003 and the data migration, and 001's A3 note stops being the current state of the world. map-hoods-heat's PRD req 3 — recorded unmet at acceptance — is satisfied by this task's completion, not retroactively by T-031.

8. Decisions

D1 — The authored source is a file, not the database

Stated in §2.1. The deciding argument is not elegance, it is reachability: the current pipeline's only path from authored data to shipped artifact runs through a credential nobody on the team holds, which is why export_hoods_geojson.py has never been run in the eight days it has existed. A source-file pipeline is also reviewable — a boundary correction shows up as a coordinate diff in a JSON file, not as an edited jsonb literal inside SQL — and it is what makes PRD req 6's "verified identical" mechanical rather than aspirational.

Rejected alternative: keep the DB as source and give the export script a --dry-run. It does not help — the script still needs a live table to read, and the authoring surface is still hand-written SQL.

D2 — Validation runs in the generator, not in CI (PRD open question 2)

CI is the wrong place because there is no CI in this workspace to put it in — and even if there were, a check that runs after the artifacts are written can only tell you that something already-committed is wrong. In the generator, a violation means no artifact is produced at all, so an invalid dataset cannot physically reach either repo through the supported path. §5.3's two extra checks cover the unsupported paths (a hand-edited bundle, an out-of-band DB write).

D3 — Single ring, hard-rejected multi-ring (PRD open question 1)

§3.4. The escalation trigger is the important half: a validator that rejects nesting is what stops "just flatten it" from becoming an undocumented data decision made by whoever hits it first.

D4 — Upsert plus scoped prune, not on conflict do nothing

§3.3. This corrects both migration 001's SQL/comment mismatch and the PRD's own description of the swap. The failure mode it prevents is the worst kind available here: a migration that runs clean, reports success, and leaves overlapping placeholder rectangles in the table for HoodHitTester to resolve by file order.

D5 — Centroid is precomputed in the bundle (PRD P1, promoted, with a reason)

HoodCatalog.centroid(of:) averages vertices. For the four shipped rectangles that is exactly right. For a real municipal polygon it is wrong in a visible way: a boundary that follows a curved shoreline or a dense street grid on one side carries many more vertices there, and the average is dragged toward the dense side — so the Hood's name label and (per map-rendering-spec.md §3) its tourist-trap marker both render off-centre, possibly outside the shape.

The fix is the shoelace area-weighted centroid — ~15 stdlib lines (§2.3), computed once at build time and stored. No new dependency, no runtime cost, and it removes a per-launch computation. Also robust to the closing-point duplication §4.2 introduces, which the averaging version is not.

This promotes a PRD P1 to a build step. Flagged as a deliberate scope call for trd-review: it is small, and the alternative is shipping a label-placement defect that only appears once real geometry lands — i.e. at exactly the moment nobody is looking for it.

D6 — places.hood_id must be on delete restrict

§4.4, C-HOOD-1 clause 1. Applies to a table this task does not own. Recorded here because §3.3's prune is what creates the hazard, and the correct place to state a cross-table invariant is the TRD that introduces the delete. places-dataset/TRD.md states the same clause; the two are deliberately identical.

D7 — Migration 003 collision with T-033, resolved on both halves

hood-place-detail/TRD.md §3.1 declares a migration 003_places_and_hood_blurb.sql that both creates the places table and adds hoods.blurb — duplicating, in one file, work that now belongs to two other tasks. Neither 003 exists on disk, and T-033 is held at trd pending Aviran's nav-row answer (BOARD.md T-033 row), so nothing has been built against it.

  • The places half is resolved by places-dataset/TRD.md §2.1 (its D1): places is defined once, in T-042, not T-033.
  • The blurb half is resolved here: hoods.blurb lands in this task's 003_hood_attributes.sql (§3.1). It is this PRD's req 4, product's data-requirements sweep assigned it here explicitly, T-040 is first in the dependency chain, and a column specified in two TRDs is a column that eventually gets two different nullability rules.

Between the two, T-033's migration 003 has nothing left in it and should be removed rather than renumbered. T-033's A1/A2 steps become a dependency on this task's 003 and T-042's places migration, not work of their own.

One further amendment T-033's TRD needs, for chief-of-staff to route (not applied by me — that document is under review by another pair): §3.4's places-tel-aviv.json seed floor drops Hood blurbs; hoods-tel-aviv.json carries them (§3.5). T-033's client reads blurb from HoodCatalog, not from the places bundle.

None of this changes a line of T-033's iOS behaviour or any contract in its §4.

D8 — provenance promoted from PRD P1 to required in the source

PRD P1 lists per-Hood provenance as a nice-to-have "for the next city." It is more than that: if the geometry is derived from OSM, ODbL attribution is a legal obligation that attaches to the derived database, and satisfying it after the fact means re-deriving provenance for rows nobody recorded it for. The cost of recording it during authoring is one object per row.

It stays out of the DB and out of the bundle — no column, no field — until someone establishes that attribution must be displayed in-app. That is a licence question sitting with Aviran (PAS-6 item 15), not an architecture question. If the answer is yes, adding a column and a bundle field is additive and changes no contract in §4.

D9 — The coverage-gap threshold is a real number, not a feeling

PRD req 1 asks for "no unnamed interior hole large enough to read as a rendering bug." Unmeasurable as written, so V7 makes it measurable without needing a municipal boundary polygon as a second input: take the union of every Hood and inspect its interior holes.

Arithmetic behind the numbers, from the shipped constant (MapScreen.telAvivCityWide, latitudeDelta: 0.14 ≈ 15.6 km) over a ~700 pt map height: ≈22 m per point at the cold-open camera. A 200 m square gap is ~9 pt — plainly visible. A 70 m square is ~3 pt — not. Hence error above 40,000 m² (200 m square), warning above 5,000 m². [ASSUMPTION] the 700 pt map height; qa can adjust both numbers against a real device without touching anything structural — they are two constants in one file.

Exterior coverage — "does the dataset reach the edges of the city a user sees" — is deliberately not validated. It needs a municipal boundary the dataset does not have, and it is a judgement call ("the area a user opening the app city-wide sees") that a human reviewing the rendered map answers better than a threshold. It stays a qa visual check.

D10 — C1, C2 and C2a carve into Build Phase 1; everything else stays Build Phase 2 (added 2026-07-31)

Decided upstream, not here. product raised it (PROGRESS.md 2026-07-31, T-033/PAS-13 entry, commit 30e002f), chief-of-staff ratified and routed it (commit 80f3a36); this amendment records it in the document that owns the steps. BOARD.md's V1 Build Phases section (b624d2f) holds this task at Build Phase 2 as a whole, and that is unchanged for every step but three.

Why three steps move. T-033 ships at Build Phase 1 with its bundled seed pinned authoritative (hood-place-detail/TRD.md §3.4.1, §8 D10). With source == .seed, its Hood sheet reads blurb from this task's bundle — and today's shipped bundle is schemaVersion 1 with keys id/name/polygon only, verified by reading the file, no blurb anywhere. Uncaught, a Phase-1 demo could only render T-033 req 2's no-blurb branch, while the blurb is half of that feature's authorizing strategy line (strategy/passenger-strategy.md:37) and all of decision #10's "local read".

Why exactly these three, and not more. C1 and C2 are pure client-side decode — a struct gaining optional fields and a decoder gaining boundary rules — with zero backend surface, which is what makes them Phase-1-shaped under the phase split's own no-backend constraint. C2a is one hand-edited fixture under an explicitly stated exception (§3.5). B1/B2/B4/B6 stay Phase 2 deliberately: pulling the generated bundle forward would drag B4, the real municipal-geometry sourcing, into Phase 1 — genuinely Phase-2-shaped effort and precisely the long pole the phase split exists to defer. A1 stays Phase 2 because it is a migration, and nothing in Phase 1 reads a column over the wire.

What this changes and what it does not. No requirement is added, cut, or rescoped; no contract in §4 moves; the schema, the validator design, the source-file pipeline and D1–D9 are all untouched. The trd-review approvals stand — this is a build-order split of already-approved steps, not new design. Two consequences worth naming: the Phase-1 bundle is briefly hand-edited, which §3.5 states as a bounded exception with C3 as its retirement; and C4's blurb/ring decode assertions ride forward with C2 (architect's own bounded call — a decode rule shipped without the test that proves it is a rule nobody checked), while C4's non-overlap tripwire stays with the real geometry it exists to check.

Risk Mitigation / decision
Real adjacent boundaries overlap by a metre from source imprecision and V6 rejects a dataset that is materially correct The most likely first failure. The fix is a snapping pass at authoring time — give neighbours identical shared vertices — not a tolerance. V6 has no tolerance knob to reach for (§2.3), which is deliberate: absorbing real overlap re-opens exactly the ambiguity HoodHitTester cannot resolve. Flagged for data-engineer as the expected first obstacle, not a surprise.
The dataset ships with every is_tourist_trap as null Very likely, and named in the PRD. Architecturally correct — tourist-trap-flag req 4 renders null as unflagged — and product-wise it means V1 launches with one of its two signals empty. Not this TRD's to solve; the proposer is data-eng/discovery-engine-spec.md and the escalation is already PAS-6 item 14. This task must not invent values to fill it.
The stdlib non-overlap predicates are subtly wrong The real cost of dropping Shapely: correctness now rests on ~150 lines this team wrote, not on GEOS. The generator's two artifacts land in two repos and one commit is forgotten --check mode plus git diff --exit-code after a regenerate proves both match the source; HoodCatalogTests catches a stale bundle; export_hoods_geojson.py --check catches a stale table. Licence terms make the sourced geometry unusable after it is authored provenance (D8) means the affected rows are identifiable rather than the whole dataset being suspect. The real mitigation is resolving PAS-6 item 15 before sourcing, which is why §6 says so plainly.
