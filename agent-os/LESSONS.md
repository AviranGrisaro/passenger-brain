**Read this file before changing any agent file, CLAUDE.md, or skill** — a rule that exists here was earned from a real failure; don't remove it without checking why it was added.

## Entry format

```
### L-NNN — <short title>
- **Date:** YYYY-MM-DD
- **Category:** process | prd-trd | qa-testing | agent-behavior | strategy | tooling
- **Scope:** general | passenger-specific
- **Evidence:** what actually happened (issue IDs with names, commits, worklog lines)
- **Lesson:** the generalized takeaway — must be true for future projects, not just today
- **Action:** none-yet (logged only) | applied → <file(s) changed, one line what changed>
- **Status:** logged | applied | verified (recurrence stopped) | failed (recurred after fix — needs a different fix)
```

## Rules for this file

- IDs are sequential (L-001, L-002, …) and never reused.
- One occurrence → log only (`Status: logged`). A pattern (2+ occurrences, or one severe miss) → apply a fix and record it.
- Before adding a lesson, search this file. If it already exists: don't duplicate — update the existing entry's Status. A recurrence after `applied` means the fix didn't work → set `Status: failed` and try a different fix.
- Newest entries at the top, under a `## YYYY-MM-DD` date header per run.

### L-052 — A claim excludes the session that starts later and not the one that starts at the same instant; two coordinators ran one founder's request in parallel and both wrote to Linear
- **Date:** 2026-08-08
- **Category:** process
- **Scope:** general
- **Evidence:** three collisions in ~20 hours, all after L-039's claim and L-049's expiry were in force. **(1)** 2026-08-07 ~17:04, `BOARD.md` inbox: *"a second, uncoordinated `chief` pass ran concurrently with this one, no claim line of its own"* — discovered because `passenger-brain 91653be` landed between two of the claiming pass's own commits. **(2)** 2026-08-08 ~07:45–07:54, inbox again: *"two concurrent `chief`-role sessions ran the identical audit against the same Aviran trigger at the same time, neither aware of the other until mid-run `Edit` conflicts surfaced it"* — both independently reached the same 16-ticket closure list and **both made real Linear API calls**, so roughly 16 issues now carry near-duplicate closing comments (`passenger-brain 2bf553c`, `8995bc2`). **(3)** the same morning, a duplicate `ios-developer` dispatch for `PAS-17`'s alias-folding cluster went out from two passes at once, caught only by an inbox line warning the router to check `git log` before acting on the second reply. The one that *worked* is the tell: at 08:10–08:2x a third `chief` session read a claim already committed at 08:10 and stood down cleanly (`passenger-brain b664247`). The protocol is sound whenever one claim is already on disk, and blind whenever two sessions read before either writes.
- **Lesson:** Read-then-claim is check-then-act, and everything between the two is a window. The fleet's claims are written *after* the reader has oriented itself — which is the natural order for a human and the wrong one for a lock — so the window is as long as a board read plus a plan, and a single founder message that fans out into two sessions lands both of them inside it. Note what does *not* fix this: an expiry (L-049) resolves a dead holder, not a simultaneous start, and neither does saying "check first" more firmly, because both sessions did check and both checks were honest. The general move is the one every optimistic-concurrency system makes: **write your claim first, then re-read and verify you won**, with a deterministic tiebreak that both racers compute the same way. The loser's cost is one wasted orientation; the winner's cost is nothing.
- **Action:** applied → `chief.md`, `project-manager.md`, `retrospective.md` (live + both mirrors) each gain, at their existing claim clause: the claim is your **first write**, before any analysis; re-read `BOARD.md` from disk immediately after committing it; if a second unexpired coordinator claim is now present, **the claim whose commit landed first wins** (`git log --oneline -- agent-os/BOARD.md`), and if that isn't yours, strike your own line, say so in the report, and stand down. Written into the existing bullets rather than added as new ones, so all three files stay within budget.
- **Status:** **superseded 2026-08-08, same day, by a real mutex — the write-then-recheck fix above was still a text protocol.** Aviran, on reading the collision report: "fix the concurrent chief sessions problem." Re-examined, optimistic concurrency over `BOARD.md` has no atomic step anywhere in it: two sessions both *append* a `PASS:` line, git accepts both (one shared working tree, sequential commits, nothing to conflict on), and the "whose commit landed first" tiebreak only adjudicates if both racers remember to re-read — a discipline requirement, the same class of fix as L-049's "remember to strike," and it fails the same way. Four lessons (L-039 → L-049 → L-052) all tried to build a mutex out of a markdown file; the file was never capable of being one. **`mkdir` is atomic on POSIX: of N concurrent callers exactly one succeeds and the rest get `EEXIST`.** That is the primitive this protocol never had. New `passenger-brain/agent-os/coordinator-lock.sh` (`acquire`/`heartbeat`/`release`/`status`), wired as step **0z** — first act of a run, before any read — into `chief.md`, `project-manager.md` and `retrospective.md`, plus both mirrors. Verified before shipping, not asserted: 20 simultaneous `acquire` calls → **1 ACQUIRED, 19 STAND DOWN, 1 token issued**; an expired holder is reaped on the next acquire and moved to `locks/reaped/` rather than deleted, so holder-leak rate stays measurable. The `BOARD.md` `PASS:` line stays and is still written — it carries the pass's scope and every agent reads `BOARD.md` — but it is documentation now, not the lock. **Shape worth carrying forward: when a coordination rule fails three times in four days, stop rewording it and ask whether the substrate can enforce it at all.**

### L-058 — Four different check tools returned a clean "nothing" that was false, and the one correction that got written down went into a status blockquote that will be struck
- **Date:** 2026-08-08
- **Category:** tooling
- **Scope:** general
- **Evidence:** **(1)** the 2026-08-07 23:28 HALT (load 270, ~108MB free RAM) was called drained and reopened 11 minutes later — `passenger-brain 4633269`, *"the process-check used name-only `pgrep -c` which silently missed live `xcodebuild`/simulator processes… Real bottleneck is swap (323M/8192M free, 96% exhausted), driven by a runaway `mediaanalysisd` simulator daemon at 286% CPU."* Its own text names the pattern: *"this is now the second time a check tool has produced a false negative this session, per L-048's Linear-listing lesson — same shape, different tool."* **(2)** and **(3)**, established 2026-08-08 and relayed by Aviran: **`timeout` does not exist on this machine** (no coreutils — `(eval):1: command not found: timeout`), so a command believed to be bounded runs unbounded; and **a zsh glob that matches nothing aborts the entire command**, so `ls *.xcodeproj *.xcworkspace` produced nothing at all when only the second glob missed — read as "no project files." **(4)** L-048 itself, 2026-08-06: a server listing read as a capability check, costing Linear a full day of writes. Four instances, four different tools, one behaviour. And the fix for the first was written **into the `> **HALT:**` blockquote on `BOARD.md`** — a status line whose entire purpose is to be struck when the condition clears, taking the `pgrep -f` correction with it.
- **Lesson:** The dangerous failure of a diagnostic is not an error, it is a *plausible empty result* — zero processes, no files, a listing without your server — because empty is what a healthy system also returns, and nothing in the output distinguishes "I looked and found nothing" from "I didn't look." Every rule this project has about proving a claim (`CLAUDE.md` rule 9, L-048) points at claims about work; this is the same demand one layer down, about the instrument. **When a check returns "nothing", prove the tool can return something** — a positive control, or a second tool that reads the same fact a different way — before you act on the silence. The second half is placement, and it is L-046 again: the correction to a shared-machine fact was filed in a **transient status artifact** rather than the environment doc, so it was scheduled for deletion the moment it stopped being urgent. Facts about the machine outlive the incident that discovered them; file them where they'll be read next month.
- **Action:** applied → `passenger-code/CLAUDE.md`'s environment section gains a **"Machine & shell facts"** block above the existing Simulator facts (same "add new ones here, not to your own agent file" contract): all four false-negative instances with the working substitutes (`pgrep -f` or `ps -Ao pcpu,rss,comm -r`, never bare `pgrep -c <name>`; no `timeout`; `setopt null_glob` or one glob per command), the general "prove the tool can return something before believing nothing" rule, and the swap/`mediaanalysisd` finding — read `vm.swapusage` beside `uptime` and `df -h /`, and treat a single load reading as a trough rather than a trend. Placed there rather than in `chief.md` because every build-running role reads it and the defect was that it lived in a disposable blockquote.
- **Status:** applied

### L-028 — A `let` optional-with-default on a `Decodable` model silently never decodes; only `var` participates in synthesized `init(from:)`
- **Date:** 2026-08-03
- **Category:** tooling
- **Scope:** general
- **Evidence:** T-035/PAS-26 build — `Place.swift:27`, `PlacesAPI.swift:39`, `PlacesCache.swift:36`, `PlaceCatalog.swift:204` all originally declared `let isTouristTrap: Bool? = nil`. Swift's synthesized `Decodable.init(from:)` excludes any stored property that is both a `let` and carries a default-value initializer expression from its decode calls — it always resolves to the initializer's value regardless of what the wire payload contains, with no compile error, no runtime error, no test failure unless a test specifically asserts the decoded value differs from the default. `ios-developer` caught it while building, fixed all four sites to `var`; `ios-code-reviewer` independently re-confirmed the fix and the mechanism during T-035's code-review pass and recommended this exact lesson. Different failure mode, same root class: a `Decodable` model's actual wire behavior is not obvious from reading the type declaration, and neither defect was caught by `xcodebuild build` succeeding.
- **Lesson:** For any `Decodable`/`Codable` model property that carries a default value, the property **must** be declared `var`, never `let` — a `let` with a default silently opts the field out of decoding rather than failing to compile or throwing. General form: any optional-with-default field on a wire model in this codebase is a specific pattern worth a specific check, not just "read the model class carefully."
- **Action:** applied → `ios-developer.md` Ground rules gains a one-line check: any new `Decodable`/`Codable` model property with a default value must be `var`, never `let`, with the mechanism stated in one sentence. `ios-code-reviewer.md` Method step 2 (correctness pass) gains a matching check to grep for `let \w+.*=.*` on `Decodable` types during review.
