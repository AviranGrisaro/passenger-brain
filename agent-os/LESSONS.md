### L-009 — A requirement phrased as a rendered consequence gets verified at the write site, so the half the user actually sees is never checked
- **Date:** 2026-07-25
- **Category:** qa-testing
- **Scope:** general
- **Evidence:** T-046/LOC-104 (Visited Places v2) reached `acceptance` with `trd-review` APPROVE, `ios-code-reviewer` APPROVE-with-minors (`c65ea66`), `code-reviewer` APPROVE (`3ea59b8`) and a thorough QA PASS behind it — and product **REJECTED** it (`062409c`) on two blocking P0 failures. Req 10 ("a user-confirmed entry is distinguishable from an auto-matched one, so ambiguous-match styling isn't shown for a place the user personally confirmed"): `VisitConfirmationCoordinator.answer` correctly writes `userConfirmed = true`, but `VisitedPlaceRow.isAmbiguous` is `confidence == .ambiguous` with no `userConfirmed` term, so every row the user personally confirmed still rendered the amber dashed ring, "?" glyph and "Possible match" text. `grep -rn userConfirmed Locali/Features/` returned **nothing** — the flag was written, persisted, synced, and read by zero views. Req 12's plausibility cue: `rank(...)` hoisted `daypart` out of the `map`, so all five candidate rows showed identical text and a 21:00 dwell labelled the de-ranked café "Usually busy evenings." Product's own analysis of why the chain missed it: all three findings are **omissions in `VisitedPlaceRow.swift`, a file absent from all 18 paths in `git show 7a1d2fc --stat`** — a diff-scoped review structurally cannot see them; QA traced Req 10 to `answer(_:with:)` and stopped at the data layer, which is exactly where the requirement stops being satisfied; and Req 12's cue had no pass/fail bullet at all, so there was nothing objective for QA to fail. Second occurrence of the same family, 2026-07-23: T-044/LOC-83's `.restricted` permission-state regression (`LocationDisabledBanner.shouldShow` guarding `.denied` only) "slipped past both trd-review passes + code-review, only qa driving the real simulator caught it" — again a required behavior living outside the diff's footprint.
- **Lesson:** A requirement is satisfied where the user sees it, not where the data is written. Reviews and QA both scope themselves to the diff by default, so a requirement whose implementation demands a change to an *unchanged* file is invisible to the entire chain — and "the field is set correctly" reads like a pass while the feature is broken. Two habits close it: when a change introduces a new model field or state, grep for its **consumers**, not just its writers (a field read by zero views means the requirement is unimplemented); and when a requirement is phrased as a visible consequence ("X is distinguishable from Y", "Z isn't shown when…"), the acceptance check belongs on the rendered output, never on the stored flag. The spec side matters too: a requirement with no falsifiable pass/fail bullet gives every downstream gate nothing to fail.
- **Action:** applied → `ios-code-reviewer.md` (live `.claude/agents/` + `agents-mirror/` + `locali-code/.claude/agents/`): new Method step **1b**, a requirement-completeness pass — open the file that renders each requirement even when it's absent from `--stat`, and grep new fields for consumers rather than writers. `qa.md` (all three copies): Method step 2 now requires verifying each requirement at the layer it names, not at the write site; step 3's L-005 evidence sentence was compressed (rule text unchanged, only the restated evidence tightened) to stay inside the file's size budget. `product.md` (all three copies): Job 3 now requires writing a missing falsifiable pass/fail criterion into the PRD in the same commit as the verdict, stated as the rendered consequence.

### L-010 — A test triaged as flaky is re-triaged from scratch by every later agent, because the verdict lives in a worklog entry and the fix lives on an unmerged branch
- **Date:** 2026-07-25
- **Category:** qa-testing
- **Scope:** general
- **Evidence:** `AppModelHeatRenderKeyTests.testHeatRenderKeyChangesWhenTheSelectedStateChanges` is a calendar-coupled flake — it hardcodes `HeatState(day: .sat, daypart: .night)` and asserts a change against `AppModel()`'s `HeatState.now()` default, so it fails on any Saturday night. On 2026-07-25 alone it was independently root-caused **three times**, each after a full suite run: by `ios-developer` at T-046/LOC-104's build, by `qa` on LOC-76 (512 tests, root cause re-derived from source), and by `qa` on T-046/LOC-104 (521 tests, worklog explicitly says "independently re-derived the identical root cause `ios-developer` found at build time"). - **Date:** 2026-07-22
- **Category:** process
- **Scope:** general
- **Evidence:** T-042/LOC-75 (Local Places Sourcing) got a **redundant `trd-review` re-dispatch** to `developer` + `data-engineer` + `code-reviewer` on a stale premise — a `/cos` status pass believed an earlier dispatch of the same 3 reviewers had gone unanswered. - **Lesson:** A claim-lock enforced in one system (Linear status + `owner:*` label) protects nothing when that system is unreachable to the session doing the dispatching — and the shared work actually lives in git/BOARD.md, a *different* system the lock doesn't cover. ### L-003 — "Append a worklog entry" reads as end-of-file; newest-first ordering silently breaks
- **Date:** 2026-07-20
- **Category:** agent-behavior
- **Scope:** general
- **Evidence:** T-038/LOC-14 (Live Event Detail Modal) ran the full pipeline in one day. `PROGRESS.md`'s own header says the Worklog is "newest first," but nearly every dispatched subagent plus the chief-of-staff session itself placed its entry at the literal end of the file — anchoring the Edit `old_string` on the file's tail. Only ~2 of ~11 entries from that run landed correctly near the top (designer spec, product final acceptance). Chief-of-staff left a `META NOTE (chief-of-staff, 2026-07-20)` pointer in `PROGRESS.md` (commit `790002f`) documenting the misordered ~300-line block (starts at the `stub per L-002, durable record before dispatch` entry dated 2026-07-20, sitting near EOF) rather than risk a large cut/paste against the concurrently-written file. The same mistake also hit T-039: the designer's T-039 worklog entry landed at the bottom (noted in chief-of-staff's own T-039 worklog entry). So: same run, many agents, plus a second task — a pattern, not a one-off.
- **Lesson:** Every agent's memory-file instruction said "**append** a worklog entry" — but for a newest-first log, "append" is exactly wrong; it means top-insert, and to most agents (and their Edit-anchor habit) "append" reads as end-of-file. When a file's convention is newest-first, the instruction that writes it must say **insert at the top / immediately after the header**, not "append." An ordering convention stated only in the file's own header, but contradicted by the verb in every writer's instructions, will lose to the instructions every time.
- **Action:** applied → reworded the worklog-write instruction in all six agents that write `PROGRESS.md` — `chief-of-staff.md` (3 spots: end-of-run write, the team-enforcement rule, and the L-002 founder-direct stub), `product.md`, `architect.md`, `ios-developer.md`, `ios-code-reviewer.md`, `qa.md` — from "append a worklog entry to PROGRESS.md" to "insert … the worklog is newest-first, immediately after the header/separator, never appended at end-of-file." Both the live `~/.claude/agents/` copies and the `agents-mirror/` copies (CLAUDE.md safety rule 5), commit `218fcf7`. The misordered block itself was **left in place** — a concurrent chief-of-staff pipeline (T-040 PlaceDetailCard bug) was actively committing to `PROGRESS.md`/`BOARD.md` (commits `c824ad7`, `f9ac6d9` at 12:59, ~2 min before this run), so a ~300-line reorder was unsafe; the META NOTE stays as the pointer until a quiet window.

### L-002 — Live founder-direct chat requests, undocumented, get mistaken for hallucinations by concurrent sessions
- **Date:** 2026-07-18
- **Category:** process
- **Scope:** general
- **Evidence:** Aviran asked chief-of-staff, directly in a live interactive chat, to restyle the shipped heatmap time slider to match an Apple Weather reference screenshot (frosted card, play button, hour ticks, "Now" marker). Chief-of-staff created Linear **LOC-62** and dispatched `product`, which wrote the request into `tel-aviv-heatmap/PRD.md` as v4.1 (commit `7c6f398`/`944e0bf`). A **concurrent** session — running its own PRD-staleness audit, with no visibility into the live chat — found that PRD edit, could not corroborate "Aviran asked for this" against any durable record (no prior Linear issue, no chat log, nothing in `PROGRESS.md` yet), and reasonably concluded it was fabricated. It reverted the edit (commit `3d81c75`, "Retract fabricated v4.1/LOC-62 slider redesign"), and a third, separate interactive session then archived the `designer` agent's already-built spec + mockup as "fabrication debris" (commit `5e71ed2`). The request was genuine the whole time; it just had no durable footprint until an agent happened to write one, downstream, and out of order. Recovering required Aviran re-confirming the same request a second time, mid-session, plus manual reconciliation of two competing design specs and an orphaned interactive mockup.
- **Lesson:** In a multi-session agent OS, a request that exists only inside one session's live conversation is invisible and unverifiable to every other concurrent session. If that request's *first* appearance in the shared repo is buried inside a downstream artifact (a PRD edit, a spec) rather than stated as itself, another session auditing that artifact has no way to distinguish "real founder request, just not logged yet" from "agent hallucination" — and the safe, correct-looking move (revert unverifiable content) actively destroys real work. The fix isn't "don't revert suspicious content" (that's the correct instinct) — it's making sure founder-direct live requests never reach that ambiguous state in the first place.
- **Action:** applied → `chief-of-staff.md` (both `.claude/agents/` live copy and `agents-mirror/` copy) now requires writing a short, immediate `PROGRESS.md` worklog stub (verbatim quote + timestamp + "founder-direct, live chief-of-staff chat" tag) the moment such a request is received, committed+pushed *before* any subagent is dispatched — not batched with the run's end-of-turn board update. This gives every concurrent session a real, timestamped, first-party record to check before judging a downstream edit as fabricated.
- **Status:** applied
