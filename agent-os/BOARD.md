## Task lifecycle (state → owner)

```
backlog → spec(product) → trd(architect) → trd-review(ios-developer/developer/data-engineer + code-reviewer)
        → build(ios-developer and/or developer) → code-review(ios-code-reviewer and/or code-reviewer)
        → qa(qa) → acceptance(product) → aviran-review → done
```

**Pre-code design gate retired 2026-08-02** (Aviran, live chief-of-staff chat via `/chief` — verbatim + reasoning in `PROGRESS.md`'s 2026-08-02 stub entry). There used to be a `design(designer)` step between `spec` and `trd`, plus `design-approval`/`design-review` sign-offs — all gone. New process: **build fast/vibe-coded first, ship, then designer redesigns after deploy.** `trd`/`build` now start straight from product's approved PRD. Designer's work moved to a non-blocking **post-ship redesign pass** — see `designer.md` — opened as its own companion task once a feature reaches `done`, never gating the original feature or any other task's build.

- **iOS vs backend split:** `build`/`code-review` fan out by surface — `ios-developer`/`ios-code-reviewer` for the Swift/SwiftUI client (`passenger-code/`), `developer`/`code-reviewer` for the Supabase backend (`passenger-brain/database/`), both pairs when a task spans both. The architect's TRD build breakdown tags each step **[iOS]**/**[Backend]**/**[Algo/Data]**.
- Marketing/research tasks: `backlog → in-progress(owner) → acceptance(product) → done`.
- Rejection loops (backward only): trd-review objection → `trd` · code-review REQUEST CHANGES → `build` · qa FAIL → `build` · acceptance REJECT → `build`. The rejecting agent writes concrete findings; the fixing agent addresses exactly those. (No more "→ `design`" fallback — there's no pre-build design step to reject back into; a design/UX finding at acceptance now goes to `build` and/or becomes input to a post-ship redesign pass.)
- `blocked-on-aviran`: strategy/scope decisions, money, external accounts (App Store, credentials), destructive ops — including every Supabase migration apply step (Aviran holds the DB credentials). Nothing else stops the loop.
- A task is `done` only after `product` ACCEPTs it against the PRD and Aviran has signed off at `aviran-review`.

Task rows: `| id | task | state | owner | updated | notes / findings / output |`

- **Strategy/scope phases** (`strategy/passenger-strategy.md`, the Scope gate above): *what features exist at all* — V1 vs. parked "Phase 2" (proximity intelligence, Scenic View, Live Events) vs. parked "Phase 3" (AI local guide, shake-to-decide). **Unaffected by this section** — Live Events and Scenic Walk are confirmed in V1 scope (decisions #32/#34); this section only says *when in the build* their real data gets wired up.
- **Build phases (this section, new):** *how V1 itself gets built and shipped*, dev-sequencing only. No feature added, cut, or rescoped — same PRDs, same requirements, different order and different real-vs-fake data at each step.

**Build Phase 2 — connect the real Supabase database, backfill with past/historical data, verify it works end-to-end.**

**Build Phase 3 — connect real live data.** Heat-area computation against live data, live events, TikTok/Reddit sourcing, etc.
