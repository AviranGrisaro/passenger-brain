V1 UX Flows

The flow, the hierarchy, and what's primary versus secondary.

Passenger is one map. You open the app and you're looking at Tel Aviv, right now — how packed everywhere is, and whether each place feels local or touristy.

You drag a slider to see the next 12 hours, tap a neighborhood to read about it, tap a place and get handed off to Maps or Waze to actually walk there. You save places — sometimes on purpose, sometimes because you lingered somewhere long enough that it saved itself — and the app quietly remembers where you've actually been. Occasionally it asks you, in passing, whether a place felt local — because that's how the map gets smarter.

There is no feed, no profile, nothing to scroll. (A private, single-user "Passport" stats screen — level + stamp grid, parked Phase 2/3, see Where Phase 2 & 3 features slot in — is not an exception to this: nobody else ever sees it, no friend graph, no following. This line still holds for V1.) If you already know what you're after, search is one tap away — a sheet you open, not a box that's always staring back at you: a product whose whole pitch is "you don't need to ask" shouldn't put a question mark in front of you by default. Every screen is either the map, or something the map handed you.

Before any journey starts

Launch behavior

First launch ever

  1. Tap the app icon. No splash screen, no onboarding carousel — the scope gate is explicit: the app opens straight to the map plus the location permission.
  2. Map renders immediately. Tel Aviv, default city-wide center, heat layer for "now", tag accents visible, both categories always shown together since there's no category filter outside the search sheet (decision #25), slider at "now". "Tel Aviv, right now" fades in and out over roughly two seconds.
  3. Location permission prompts lazily — the OS system sheet, never a custom in-app screen (decision #8). It does not block map interaction.
    • Granted: map animates to real location, "you are here" marker appears, and Places-detection can begin — in a limited, foreground-favoring way at this permission level. Reliable background tracking needs the Always upgrade below, not yet asked for at this point.
    • Denied: map stays at the default city-wide center — walked end to end in Journey 6.
  4. User explores. Pan, zoom, drag the slider, tap a zone or spot, open search if she wants to narrow by category or find something specific. The steady state almost every session lives in.

Every subsequent launch

  1. Tap the app icon. Map renders against whatever permission state iOS already recorded — no re-prompt.
  2. Granted: opens already centered on current location, no animate-in beat. Denied: opens at the same default city-wide center as first run.
  3. Slider always resets to "now." DESIGN CALLPersisting a stale "+3h" from last session would misrepresent live data the instant the app reopens. "Now" is only ever valid at the moment you look at it.

Permission sequence — three asks across a session, not one gate at launch

Decision #8 keeps cold open permission-gate-free — still true, still just the one lazy When-In-Use location prompt above. But V1 now has three distinct system permissions to eventually ask for, not one: Location — When In Use (cold open, unchanged), Location — Always (needed for dwell-based auto-save and for background geofence detection to actually fire — Places population likely needed this all along; decision #26 is what finally makes it explicit rather than hand-waved as generic "location permission"), and Notifications (decision #24, the post-visit toast). Asking for all three near launch would be a permissions gauntlet the strategy never signed up for.

DESIGN CALL, FLAGGEDProposed sequence:

  1. Cold open: Location — When In Use only, exactly as specified above. Nothing else.
  2. First real visit — the first time the app can tell she's dwelling somewhere or has just arrived: a single in-app priming line first — plain language, something like "Let Passenger notice your visits, even when it's closed?" — not a system dialog yet. If she continues, two system prompts fire back to back, both explained by that one line: Location — Always, then Notifications.
  3. If she declines the priming line, or denies either system prompt: no repeated asking, ever. Manual saves keep working regardless. Auto-save, geofence-detected Places entries, and the local-QA notification simply don't happen for her — degraded, not broken, not re-prompted.

This turns three scattered asks into two moments — one at launch, one contextual pair later. This is a proposal, not a confirmed sequence; see Open questions.

Six journeys, start to finish

End-to-end journeys

Chosen to partition V1's surface without duplicating it: two discovery contexts (tourist and resident, who use the same map differently), one return visit, one feedback loop, one search-first context, and one full pass under degraded conditions — because location-denied and offline don't touch one step, they touch nearly every step at once.

Search earns its own journey rather than folding into an existing one: every other journey starts with reading the map — a zone, a slider drag, a saved list — while search is the one path that starts with already knowing what you want and skips the reading entirely. It sits right before the degraded run: a normal alternate entry point, followed by the stress-test pass that touches everything that came before it, search included.

Every V1 interaction appears in at least one journey. Where something can go wrong, it's attached to the step where it bites.

A seventh journey follows these six — a Phase 2/3 preview, not committed V1 scope, not counted among the six above.

Journey 1 · Discovery, cold

Just landed, knows nothing

A tourist, first time opening the app, has just landed in Tel Aviv.

Tap icon→ Map renders→ Zone sheet→ Spot sheet→ Goexits to Maps/Waze

  2. A few seconds in, the OS location sheet appears without blocking the map underneath. She taps Allow — the map animates to her real location, a "you are here" marker appears, and Places-detection can begin in its limited, When-In-Use form (the reliable background version waits on the Always upgrade).
  3. She taps a zone near her hotel, both categories mixed together in the list that opens. A bottom sheet slides up with a hand-curated blurb and a scrollable list of tagged spots — short enough (decision #12's bounded curation) that she doesn't need to narrow it by category to scan it. If there's no data hereThe sheet reads "Nobody's mapped this corner of Tel Aviv yet" instead of an empty list. She keeps browsing; nothing broke. Decision #25's real costIf she'd wanted to narrow to just "Things to do" first, that's no longer a single tap — she'd have to open search and select the category there (Journey 5's territory), which costs more than the old always-visible chip did.   4. She taps a spot in the list — a rooftop bar tagged Local, in a zone where heat is already climbing for this hour. Spot sheet opens: name, category, vibe tag, save icon, "Go".
  5. She taps Go. Passenger hands her straight to native Maps/Waze with the destination pre-filled — an exit, not a screen inside Passenger. She never sees an in-app route.
  6. She walks there using Maps/Waze; Passenger is backgrounded. If the geofence monitor catches her arrival, Passenger fires a local notification — the local-QA ask from Journey 4 picks up from here, not repeated in this journey.

The degraded run

If location was denied outright, she loses the other two feed paths and any chance to answer a local-QA question — but pure offline with location granted doesn't cost her any of that; everything still happens, it just syncs late. Nothing crashes and nothing lies to her about data being fresher than it is — that's the bar, not full feature parity.

Getting around without a nav bar

Navigation model

No nav bar, no tab bar, no feed. Three surface types, and one exit.

Map chrome

Always on screen, never dismissed — heat and tag layers, slider, fading title, near-me button, Search icon, Places icon (one icon now, not two — decision #26 merges Saved and Visited). Category chips no longer belong here (decision #25 — they live inside the search sheet now). The neighborhood button lives here too, with one difference: it's conditionally present, only rendering at neighborhood zoom, rather than visible from any state the way the rest of this list is.

Sheets

Partial height, swipe down or tap outside to dismiss — zone sheet, spot sheet, search sheet (now including the category chips), Places list (merged, decision #26).

The local-QA toast

Not a sheet. Top-anchored, non-blocking, and — unlike everything else here — never invoked by the user; it arrives on its own, dropped in response to a system notification tap (decision #24), and dismisses on its own too, either on answer or after a few seconds ignored. It can appear over whatever the app is currently showing, since it doesn't require any particular screen underneath it. See Journeys.

"Go" is not a surface at all

It's a system hand-off to native Maps/Waze, which exits Passenger entirely. Returning afterward drops the user wherever iOS left off — typically the spot sheet or the map. Passenger doesn't reconstruct any state for this, because it never built a screen to leave in the first place.

The zone sheet now has three doors, one destination. Tapping a zone shape, tapping the neighborhood button, and selecting a neighborhood result from search all open the exact same zone sheet — none of them a different surface, none changing what depth costs. The button and search just give an always-there polygon tap two more reliable front doors.

Depth rule: 2 levels, no more, while inside the app

Map (0) → zone sheet (1) → spot sheet (2) is the deepest path that stays inside Passenger. Places reaches the same maximum by a shorter route, skipping the zone step because you already chose the place.

Search holds at the same ceiling, but gets there two different ways depending on the result type — worth confirming rather than assuming, since it isn't the same shortcut in both directions. Search (1) → spot sheet (2), for a place-name or keyword result, matches the Places pattern exactly — it skips the zone-tap step because the user already named what they want. Search (1) → zone sheet (2), for a neighborhood result, isn't a shortcut at all — it reaches the same zone sheet a direct map tap would reach at level 1, just one level deeper, because the query itself occupies level 1 first. Either way, 2 stays the ceiling.

Nothing in V1 needs a third in-app level. The one feature that would have required it — Scenic View — is Phase 2, and keeping it out is exactly what holds this rule at 2 instead of 3.

Dismissing any sheet always returns exactly one level up.

The local-QA toast (decision #24) sits outside this rule entirely — not an exception to track, but because it was never a navigational level to begin with. It isn't reached by descending from anywhere, and dismissing it doesn't return "up" to a prior screen, since it never displaced one.

What the map shows, when

Map state & density

Per note 2: the requirement is plain — the user can tell tourist-vs-not, via Local/Mix/Tourist. Everything below is my proposed solution to that requirement, already through one feedback loop with Aviran (badge → stroke). Left as stated fact, not reopened as a question, since the rest of the doc is written against it — flagged in Open Q12 in case that reading is wrong.

Revised this round — the fix over-correctedAviran's pushback, verbatim: "how do you show tag layer on every location on the map? its gonna be too much information on one layer." The last pass moved tag to neighborhood-zoom-only badges and solved the density problem — but that left tag with zero rendering at city-wide zoom, the zoom cold open actually shows, while Feature hierarchy still claimed tag was "on by default, the first thing you see," 0 taps. Aviran caught the contradiction: heat-only at cold open is the half of this product anyone already gets from Google Maps. The fix is a channel change, not a placement change — heat keeps the fill, tag moves to the zone's outline stroke, a channel nothing else was using, so it can be visible at every zoom without reopening the density problem.

Zoom levels, and where each layer actually lives

  • City-wide — heat as neighborhood-scale blobs. Tag renders here now too — a zone outline stroke, but only on Local zones; Mix and Tourist stay unstroked. No word labels yet (too fine to read at this scale), no pins.
  • Neighborhood — zone boundaries visible, heat as zone-level stepped-band fill. Outline stroke on Local or Tourist zones (Mix still unstroked), plus a word label at the centroid — the only zoom where the word appears. Still no spot pins.
  • Close — individual spot pins appear. The zone's outline stroke persists at whatever boundary is in view (no label at this zoom). Pins themselves still carry no tag signal at all — heat continues exactly as it rendered at neighborhood zoom; pins exist only to mark a location and category, plus a ring accent for anything already in the viewer's Places list (decision #26, below). Tapping a pin opens the spot sheet, where the vibe tag renders as what it always was underneath the map: a word in a sheet, not a decoration competing with dozens of others.

DESIGN CALLWhether spot pins should carry tag at all was left open for me to decide. I'm calling it no, never — not "no badge, but a tag-colored pin shape instead." Even a pin whose own shape and fill encode tag still asks the eye to individually parse every pin in a crowded block one at a time; the only fix that survives Florentin at 8pm is moving spot-level tag off the map surface entirely, onto the zone sheet's list, where it's a word read one row at a time. Decision #12 still keeps spot-level localness data — this only changes where it renders. Pin anatomy, clustering, and exact labels are in the companion spec linked below.

DESIGN CALLWhy city-wide only strokes Local, not Tourist too: extends the existing Mix-is-silent discipline one level further rather than carving out an exception. A handful of green pockets across the city is a glance; a fully outlined city in two colors is a map you have to parse. It also lines up with what "busy" even means at that scale — heat itself is only coarse blobs at city-wide, not the zone-level precision the busy+Tourist warning needs, so that warning has no coherent city-wide granularity to begin with. City-wide becomes a map of where to trust, matching the north star's actual question, not a map of every liability too.

Slider hours

Unchanged by any of this — heat is the only time-variant layer, tag isn't, so a zone's tag stroke never moves when the slider does, regardless of which granularity it's currently rendering at.

Mix renders nothing — no stroke, no label — at any granularity

With three tags, Mix is the unmarked middle and almost certainly the most common single value — marking it would be pure clutter carrying zero information. A zone gets a stroke only for Local or Tourist; a blank zone reads as Mix. DESIGN CALLA zone with no curated data yet also renders blank, identically — the map surface doesn't try to distinguish "confidently Mix" from "not yet rated," and that's an accepted trade-off: tapping in always resolves which one it is, the same way every other empty state in this doc resolves "no data here" on contact rather than pre-announcing it on the map.

The packed + touristy trap — replace, don't stack

A zone that's simultaneously busy and Tourist-tagged doesn't get two decorations — it gets one stroke treatment, in a distinct warning form, replacing the plain Tourist stroke outright (and the label reflects it, at neighborhood zoom). Never two elements competing for the same handful of square millimeters (Von Restorff: only one "special" element per view). Busy + Local still never gets a warning treatment of any kind — the absence stays legible precisely because the warning exists for the other case, and that logic survives the move to zone granularity unchanged. The "very local but temporarily busy" case holds too: heat is time-variant, tag isn't, so a Local-tagged zone spiking busy at 9pm reads as "busy AND local," never as evidence it turned touristy.

Personal places on the map (decision #26)

A place already in the viewer's Places list gets a ring accent on its pin at close zoom — binary (yours or not), not a three-way encoding of manual/auto/visited the way the list itself shows; that nuance stays list-only, on purpose, so the map doesn't reopen the exact density mistake tag-per-pin was. Safe at a scale tag-per-pin never was, because it's bounded by one person's own history, not by the city's spot count. Full reasoning and the exact rendering rule are in design/map-rendering-spec.md.

Pin anatomy, clustering & accessibility labels

Specified in the companion doc, not here — that level of rendering detail would bloat a flows document: design/map-rendering-spec.md (markdown only, no reading-view twin). What belongs here is the structural fact that governs it: the busy+Tourist warning and the Mix-is-silent rule both live at the zone's stroke, not spot pins.

Search results and the map — a real design call, unaffected by the tag-density fix above

Decision #23 settles that results carry heat and tag and honor the slider hour, but not what the map itself does visually while the search sheet is open.

DESIGN CALLWhile results are showing — from a typed query or a tapped category chip, decision #25 makes these the same mechanic — the map underneath dims everything except the matching pins or zones. This is temporary: the moment a result is selected and the destination sheet opens, the dimming clears and the full unfiltered heat/tag view returns underneath.

What a category selection does once the search sheet closes

Resolves the old open question about category filtering, now that chips live only in search.

DESIGN CALLA category selection is scoped to that search session only. Dismissing the search sheet — whether or not a result was tapped — always drops the filter and returns the map to its full, unfiltered heat/tag view, both categories mixed. It never persists as a standing map-level filter. Reasoning: with chips no longer on the map, there's nowhere left to show that a filter is silently still active — a persisted-but-invisible filter is exactly the kind of hidden state a map whose whole premise is "legible at a glance" can't afford (the map is Sovereign and must stay fully legible on its own; the search sheet is Transient, and its effects should die with it). Every fresh search-sheet open starts with both categories active by default, consistent with the rest of this doc's no-persistence pattern.

Decisions this doc couldn't make

Open UX questions

  1. Q1 Local-QA notification cadence — revisited for a push mechanic, where tolerance is much lower

    My old recommendation ("roughly once per session") doesn't translate — a notification isn't session-bound, and firing one on every detected visit will burn goodwill fast. Decision #26 now gives auto-save an explicit number — 20 minutes — for a related-but-not-identical purpose (worth saving vs. worth asking about).

    Recommendation: cap at one local-QA notification per day, full stop, regardless of how many visits are detected that day, and default to reusing the same 20-minute dwell threshold rather than maintaining two separate numbers with no obvious reason to differ — see Q9 if asking should have a stricter bar than saving.

  2. Q2 Lazy location permission — exact trigger

    Decision #8 says "lazy," but not whether that's an automatic system prompt shortly after the map renders, or only on the first tap of near-me.

    Recommendation: auto-prompt once, softly, a couple of seconds after the map first renders. Starts Places-tracking (in its limited When-In-Use form) as early as possible without blocking the first look at the map.

  3. Q3 Does the slider ever look backward?

    Taken here as strictly forward-only, now → +12 hours. Worth confirming there's no case for "it was busier here 30 minutes ago" before this locks into the build.

  4. Q4 Background-location reliability — now load-bearing for three things, not one, and it needs "Always," not "When In Use"

    Places population, the dwell-based auto-save trigger, and the local-QA notification all depend on the geofence/dwell monitor running while Passenger is backgrounded. Does iOS reliably keep Always-level background location running through a Maps/Waze hand-off and the walk that follows, or does backgrounding risk losing the signal all three features depend on?

    Recommendation: confirm this with the architect before treating any of Places' automatic paths (decision #26), the notification trigger (decision #24), or the old Visited-only design (decision #16, now superseded) as settled — if Always-level tracking is shaky, all three need a fallback conversation, not just one of them.

  5. Q5 Does the busy + Tourist warning stroke (zone-level) need its own VoiceOver label?

    It's a display-time computation, not a stored tag, so it won't inherit whatever label the plain Tourist stroke already carries.

    Recommendation: give it an explicit label — "busy and touristy, worth a second look" — rather than relying on VoiceOver to read heat and tag separately and expecting the combination to be inferred. This now has a sharper edge: the Mix-is-silent rule means a sighted user reads "no stroke" as Mix, but VoiceOver can't read an absence — resolved in full in design/map-rendering-spec.md's accessibility section, kept coherent with this question rather than answered twice.

  6. Q6 Does the search sheet keep recent searches?

    There's no account and no persistence story anywhere else in V1 — the time slider itself resets to "now" every launch on purpose, and category selections now die with the sheet too.

    Recommendation: default to no persisted history across launches, matching that pattern. A session-only recent list, cleared on relaunch, is a reasonable middle ground if a completely blank field on every open feels too cold — but that's worth Aviran's read, since locals searching the same handful of things repeatedly is a real, recurring use case this would help.

  7. Q7 What does the neighborhood button do when the viewport straddles two zones roughly evenly?

    At the boundary between Florentin and Neve Tzedek, say, with no single dominant neighborhood in view.

    Recommendation: don't guess at a winner. Hide the button entirely below some clear-dominance threshold (e.g., one zone needs to cover meaningfully more than half the viewport) rather than risk sending someone into the wrong neighborhood's sheet with false confidence — tapping either zone shape directly still works regardless.

  8. Q8 Notification-permission-denied is a real, named coverage gap, not a small one

    With no spot-sheet fallback (decision #24 replaces, doesn't supplement), a user who denies notification permission — or who consistently ignores/dismisses the notification — never gets asked about any visit, ever, in V1. This directly compounds the strategy's own named risk: V1 runs on goodwill alone, and if that doesn't produce enough answers, the algorithm has nothing to check itself against.

    Recommendation: accept this trade for now — a second ask mechanism to plug the gap reintroduces exactly the complexity decision #24 just removed — but track the notification opt-in rate as a real launch metric, not an afterthought. If it's low, that's a signal to revisit this doc, not just a data point to note.

  9. Q9 Should the local-QA notification reuse decision #26's 20-minute auto-save threshold, or need its own?

    Q1's refined recommendation defaults to reusing it. The case for a separate, stricter number: a push notification is a bigger interruption than quietly adding a row to a list, so "worth asking about" could reasonably demand more than "worth saving." Needs data-engineer/architect input either way, not a pure UX call.

  10. Q10 Permission sequence — flagged hard, per the instruction that came with decision #26

    V1 now needs three system permissions (Location When-In-Use, Location Always, Notifications) for a product whose decision #8 explicitly rules out a permission gate at launch. Launch behavior proposes a concrete ordering — one prompt at cold open, then a single in-app priming line before Always and Notifications fire back to back at the first real visit — but it's a proposal, not a confirmed sequence.

    Recommendation: confirm the proposed ordering, or replace it, before this becomes a build spec — don't let three unordered permission asks reach ios-developer by default.

  11. Q11 The merged Places list's name and provenance display — recorded open on decision #26, and I'm proposing rather than leaving blank

    Name: "Places." Provenance: a short word per row — Saved / Auto-saved / Visited — with manual save always winning the displayed label if it ever applies to a place, auto-save next, plain Visited last, so a place never shows two conflicting explanations for why it's in the list.

    Recommendation: confirm both, or overrule either — everything in Feature hierarchy, Journeys 3–4, and design/map-rendering-spec.md is written against this proposal, so a change here is a find-and-replace, not a redesign.

  12. Q12 Does note 2 ("don't write solutions") reach past the tag-layer line into Map state's rendering solution too?

    Fixed the literal flagged text in Feature hierarchy (plain requirement now, not "Localness accent"). Left Map state's stroke/zoom solution as stated fact, not reopened — it already passed one feedback loop, and the nav model, diagrams, and all six journeys are written against it.

    Recommendation: treat Map state as settled unless told otherwise; confirm which reading was intended.

  13. Q13 Stamp collection / Passport (Where Phase 2 & 3 features slot in, Journey 7) — three questions parked in strategy.md, not re-litigated here

    Per-city flavor names for the tier ladder (explicitly deferred cosmetic idea, not level-logic); confirming "Passport" as the surface name instead of "profile" (needs Aviran's explicit sign-off — "profile" is a literal scope-gate tripwire); and whether this is the same mechanic as Phase 3's points system or two systems that coexist. Full text lives in strategy/passenger-strategy.md's Open questions section — not restated here per the doc-ladder rule.
