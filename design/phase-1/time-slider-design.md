## 0. Scope discipline

This spec covers exactly the four components the PRD/board hand-off names, no more:

1. **Hour slider control** — 13 hour-snapped positions (now → +12h), a fixed "now" tick, a visible numeral
2. **Heat modal container** — the chrome that houses the slider, opened from the heat button in the 3-button nav row
3. **Selected-hour store** — the single in-memory source of truth every hour-bound layer reads
4. **VoiceOver step behavior** — discrete, announceable steps, not a continuous-drag-only gesture

**Deliberately absent, per the PRD's own "Not in scope" line:** the heat layer's own rendering rules (bands, opacity, zoom behavior — T-031's territory, untouched here); the layer toggles that share the heat modal's chrome (each toggle belongs to the layer it switches — the live-events toggle is T-034's); anything past +12h or before now; scheduling/reminders tied to a future hour. Where the mockup has to show a toggle row to prove the modal's layout, it renders a locked/stubbed row labeled with its owning task, exactly as T-031's mockup stubbed the Hood sheet. **Correction, REJECT fix pass:** the heat layer itself has **no on/off toggle in V1 at all** — checked directly against `map-hoods-heat-design.md`, which lists only demo/instrumentation toggles (Network, Density-gap, Map-bounds, VoiceOver-label preview), none of them an app-level "Heat layer on/off" switch. T-031 renders heat as an always-on baseline layer, never optional, so this spec no longer claims that non-existent toggle is "T-031's" — the mockup's stub row now reads "always on, no toggle in V1" / "baseline" instead of attributing it to another task's unbuilt work.

## 1. Flow

**Entry points, plural — v2 addition.** The heat button (below, unchanged) and a vertical edge slide on either live phone edge (new, this pass, PRD req 7). Both write the same `selectedHour` — there is one control with two ways in, not two controls (Q3, carried as **[ASSUMPTION]** from the PRD; see §5b).

### 1.1 Button/modal path — unchanged from v1

```
Heat button tap
  → Heat modal opens as a floating card, anchored just above the persistent nav row
      (not flush to the screen edge — see §2's architecture note on why)
      → Slider shows the hour this session left it at — "now" on a fresh cold launch,
        otherwise wherever the user last set it this session
      → Drag the thumb, tap a point on the track, or step via VoiceOver/keyboard
          → Thumb snaps live to the nearest of 13 whole-hour stops — never rests between two
          → Cannot pass "now" on the left or "+12h" on the right — no wrap, no overshoot
          → Every hour-bound layer on the map repaints for that hour; camera, zoom, and any
            other open sheet are untouched
      → Exit paths, all returning to the plain map with the hour retained:
          → Swipe the card down
          → Tap the dimmed map area behind it (tap-outside)
          → Tap a different nav button (search or profile) — closes this modal and opens
            the other; never stacks (`ux-flows.md` §2.1)
```

**Modal exclusivity + persistence (§2.1's rule, this is where it's built):** only one of {search sheet, heat modal, Profile screen, Places list} is ever open. Switching to a different one closes the heat modal but does **not** reset the selected hour — the hour is session state living above the modal, not state owned by the modal's own lifecycle. Reopening the heat modal later in the same session shows the hour exactly where it was left.

**Cold launch (every app relaunch):** the selected hour re-resolves to "now" against the real clock, regardless of where the previous session left it (PRD req. 3). This does not force the heat modal open — cold launch returns to the plain map, same as any other launch; the slider only shows "now" the next time the modal is opened.

**Exits:** there is no exit *from* the map here — this is a preview/adjustment control, not a hand-off. Swipe-down, tap-outside, and nav-button-switch are the only three ways out, and all three preserve the session's selected hour.

### 1.2 Edge-gesture path — new, v2, PRD req 7

```
Finger touches down inside a live edge's capture zone (either phone edge on iPhone;
left only on iPad — §2's per-idiom row, Q2)
  → No reveal step, no second gesture. The hour starts tracking the finger immediately.
  → Idle hint (a thin vertical bar, always faintly present on a live edge) is replaced by
    the active vertical track: 13 hour-stops, a "now" tick at the bottom end, a floating
    numeral readout beside the finger
  → Vertical position maps directly to hour — touching down anywhere and continuing to
    slide toward either end of the usable band reaches "now" or "+12h" without lifting,
    regardless of where the finger first landed (PRD req 1's widened reachability bullet)
  → Up = later, down = earlier — identical on both edges, because both read the same
    position-to-hour function (§2, not a per-edge special case)
  → Horizontal movement during the slide does nothing — only vertical position writes
    the hour (PRD req 7)
  → Every hour-bound layer on the map repaints live, same as the button path — this is
    the same `selectedHour`, not a shadow copy (Q3)
  → Finger lifts → the hour under it at that instant is the selected hour and holds for
    the session (PRD req 4). The active track and readout disappear immediately — no
    second gesture commits or clears them. The idle hint returns.
```

**Unavailable while any sheet is presented (Q6, §5b):** touching down on an edge while the heat modal, search, or profile sheet is open does nothing — no track appears, no hour changes. The idle hint itself hides the instant a sheet opens, so there's nothing inviting a touch that wouldn't do anything. The heat button remains the way to change the hour in that state.

**Unavailable on an OS-reserved edge (Q2, §2):** on iPad, the right edge is system Slide Over and is never claimed by this control. Its idle hint never renders there; a faint neutral ghost mark takes its place instead of a silent blank, so a reviewer or a `qa` pass sees *why* nothing responds rather than reading it as a missed build.

## 2. Screens & components

| Component | What it is | SwiftUI-native pattern |
|---|---|---|
| **Heat modal container** | Small floating card holding the slider (+ each layer's own toggle, stubbed here), opened by the heat nav button | **Architecture note, not a system `.sheet()`:** building this as a literal `.sheet(isPresented:)` would present above the *entire* screen, including the persistent nav row underneath — which breaks the direct nav-button-switch requirement in `ux-flows.md` §2.1 (tapping Search or Profile while the heat modal is open must close it and open the other, without the user dismissing first). The mockup proved this out concretely: an early build anchored the card flush to the screen bottom and it visually swallowed the nav row. The fix, carried into this spec: the card is a **custom overlay** in the map's own view hierarchy — a `ZStack` layer above the map content but *below* the nav row's own layer — anchored a fixed distance above the nav row (not `bottom:0` of the screen), sized to its content, sliding in with `.transition(.move(edge: .bottom)).combined(with: .opacity)`. This keeps the nav row reachable and visible at all times, satisfying the exclusivity rule without a dismiss-first step. Flagging this explicitly for `architect` (§8) since it's a real deviation from "just use `.sheet()`," the default assumption a TRD might otherwise reach for. **Fix, REJECT finding 2:** the same overlay's footprint (bottom 104px–~398px on the mockup's 812pt frame) sits directly under two *other* persistent Primary chrome controls this task doesn't own — near-me (recenter) and the Places icon (`ux-flows.md` L44, L46) — both floating buttons at `bottom:128px`, same horizontal band, same z-tier as the nav row. Unlike the nav row, neither has a direct-nav-switch requirement to preserve, so the correct call is different from §2.1's nav-row rule: **near-me and the Places icon fade out (opacity → 0, non-interactive) the instant any nav-row modal opens, and fade back in the instant it closes** — they don't need to stay reachable *through* the modal the way the nav row does, they just need to not visually collide with it. `ios-developer` implements this as a simple `.opacity()`/`.allowsHitTesting()` pair driven by "is any nav-row modal open," honoring Reduce Motion the same as the modal's own transition. Confirmed fixed in the mockup (`.chrome-hide` class + `setFabsVisible()`, toggled on every `openView()`/`closeAll()` call). |
| **Hour slider control** | 13 discrete stops: now, +1h … +12h | SwiftUI `Slider(value: Binding<Double>, in: 0...12, step: 1)` bound to the store's `selectedHour`, **not** a freeform continuous slider with rounding applied after the fact — the `step:` parameter is what makes the invalid (off-hour) state structurally impossible rather than corrected post-hoc (Poka-Yoke, §7). A custom `GeometryReader`-driven track overlay adds the fixed "now" tick mark and per-stop hairlines the native `Slider` doesn't render on its own — the native control still owns the drag gesture, value clamping, and accessibility semantics; the overlay is purely decorative on top of it. **Touch target note for `ios-developer`:** the visible thumb graphic can be drawn smaller than 44pt for visual weight (this spec's mockup uses a 28pt dot), but the *tappable/draggable* area — the full `Slider` control's frame — must not be shrunk to match; keep the control's own frame height at ≥44pt regardless of how slim the visible track/thumb render (Fitts's Law, §7). |
| **"Now" tick + numeral** | A fixed visual anchor at the left end of the track, plus a always-visible numeral stating the selected hour | The tick is a distinct **shape** (a short vertical bar, taller than the round per-stop hairlines), not a color difference — so it reads in grayscale and for colorblind users exactly as it does in full color (§3, "never rely on color alone"). The numeral (`Text`, semantic style, tabular-figure rendering for the digit) sits beside the track, updating live on every step; it is the non-positional channel for "how far forward am I looking," since thumb position alone isn't legible enough at a glance for every user (PRD req. 5). |
| **Selected-hour store** | The in-memory `selectedHour` this control writes to and every hour-bound layer reads | This is T-031's `DensityStore.selectedHour` seam, flagged explicitly in that spec's §2 Density feed client row and §8 item 2 — T-032 is the first (and so far only) writer. No new data model: the store already fetched all 13 hour buckets with the map's initial load (PRD's Technical design), so moving the slider is a local re-read against already-cached data, never a network round trip — this is what makes the <400ms repaint budget realistic. The store itself is session-scoped, in-memory only — **never written to `UserDefaults`/`AppStorage` or any other persisted store**, since PRD req. 3 requires "now" to re-resolve against the real clock on every cold launch, not against a cached value from the prior session. A fresh `DensityStore` instance on launch always initializes `selectedHour` to the index representing "now," recomputed against the system clock at that moment — never a stored index carried over. |
| **VoiceOver step behavior** | Every step is discrete and announced; the control is not continuous-drag-only | Because the underlying control is a native `Slider` with `step: 1`, VoiceOver's built-in adjustable action (swipe up/down while focused) already moves exactly one step per gesture and speaks the new value automatically — this is semantic-first (§5: "real `Button`/`Label`/native controls before manual accessibility hacks"), not a custom gesture recognizer reimplementing what the platform already does correctly. The one thing this spec adds on top: `.accessibilityValue()` is overridden to speak the human string ("+3 hours, 9 PM") instead of the raw slider value ("3 of 12"), so the same "now" + absolute-time framing sighted users see is what VoiceOver users hear. Hardware keyboard (external keyboard / Full Keyboard Access) gets the same discrete behavior via arrow-key increments on the focused control, at no extra engineering cost — it's the same `step`-driven semantics, not a second implementation. |
| Layer toggle row (stub, not this task) | Placeholder rows for Heat layer / Live events layer switches | Rendered locked/dimmed in the mockup. **Corrected, REJECT should-fix 3:** the live-events row is labeled with its real owning task (T-034), unchanged. The heat row is **not** a stub for another task's future work — checked directly against `map-hoods-heat-design.md`, which defines no on/off toggle for the heat layer at all (only demo/instrumentation toggles). The heat layer is an always-on baseline, non-optional in V1, so the row now reads "always on, no toggle in V1" / a "baseline" pill, rather than falsely attributing an unbuilt toggle to T-031. |
| **Day-boundary flag ("next day")** — *added this pass, REJECT should-fix 4* | A small pill beside the numeral, shown only when the selected hour's absolute clock time falls on the calendar day after "now" | A conditional `Text("next day")` inside a `Capsule()`, present only while the crossed condition holds — computed purely by comparing the selected offset's resulting wall-clock time against "now"'s calendar day; no new data source, display-only. Text color uses the same muted token as the track's end labels (`--fg-muted`-equivalent, fixed in this pass — see §4/§7), so it clears 4.5:1 against its own tinted background in both themes rather than getting a one-off color. **VoiceOver:** the same `accessibilityValue` string the VoiceOver step behavior row already overrides (§2 above) appends ", next day" whenever the flag is showing, so VoiceOver users get the same information sighted users get from the pill, not a second, silent channel. This is a readability aid layered on top of the existing numeral/tick — it does not change how any hour bucket is stored, fetched, or keyed; see §8 item 4 for the still-open backend question this doesn't answer. |
| **Edge capture zone** — *new, v2, PRD req 7* | The real pointer/touch hit-region at each live screen edge | 24pt wide, inset 64pt from the top (clear of the status bar and the Notification Center / Control Center reveal zones) and 40pt from the bottom (clear of the home indicator). 24pt is half the 44pt Fitts's-Law minimum (§7) — wide enough to reliably win gesture-initiation against MapKit's own pan recognizer (`architect`'s finding, `PROGRESS.md` 2026-07-31) while claiming the smallest band that still does that. **Per-idiom, Q2:** both edges live on iPhone; on iPad the right edge is system Slide Over and is permanently excluded — left edge only. Built as a `UIGestureRecognizer` (or `DragGesture` with a `.highPriorityGesture`/`simultaneousGesture` composition, `architect`'s call at the TRD) anchored to each live edge's frame, **not** a full-screen gesture filtered by touch location — the zone's own bounds are the filter. ## 3. Every state

Per `design-principles.md` §4 and the PRD's own P0 requirements 2, 3, 4:

| State | Behavior |
|---|---|
| **Modal closed (default)** | The slider doesn't exist on screen at all — no persistent chrome for it, matching `ux-flows.md`'s "time slider itself isn't on screen at cold open" rule. The map reads whatever hour is currently selected in the store (defaulting to "now"), with zero indication on the map surface of *why* — that's the modal's job when opened, not the map's. |
| **Modal open, at rest** | Numeral, "now" tick, and thumb position all agree with the store's current value. No loading state exists here — all 13 buckets are already in memory (PRD's API contract), so there is nothing to wait for between opening the modal and it being fully interactive. |
| **Mid-drag** | The thumb tracks the pointer live, snapping to the nearest whole-hour stop continuously (not just on release) — this is the Poka-Yoke choice: the control is never observably in an invalid, off-hour state, even transiently, rather than allowing a free-floating position that gets corrected only when the finger lifts. The map's heat layer repaints on every snap-to-a-new-stop, not only on release, so dragging *is* the live preview, matching the PRD's "map repaints for the selected hour" requirement rather than treating drag and commit as separate steps. |
| **Hour has no data (empty)** | This is T-031's rendering rule, inherited unchanged: the affected Hood(s) render with no fill, no error copy, on the map underneath — the modal itself shows nothing different when the selected hour happens to be a gap; the slider has no awareness of "does this hour have data," it only holds a value. (PRD req. 2's silent-empty requirement is satisfied at the rendering layer, not duplicated here.) |
| **Feed unreachable / offline** | Same non-event for the slider: all 13 buckets were fetched once at map load, so being offline afterward doesn't change what the slider can do — dragging still works, still repaints instantly, against whatever was last cached (T-031's offline state owns the "showing cached data" indicator; the slider doesn't add a second one). |
| **Closing via nav-button switch** | Per §2.1's exclusivity rule: the modal closes, but `selectedHour` is untouched — a different nav surface (search sheet, Profile) opens in its place. Reopening the heat modal shows the same hour, not "now." |
| **Cold launch** | `selectedHour` resets to "now," resolved against the real clock at that moment — not a value carried over from the prior session, not the hour the app happened to be showing when last backgrounded (PRD req. 3, and the PRD's own flagged open technical question about foregrounding across an hour boundary — see §8). |
| **Selected hour crosses midnight** — *added this pass, REJECT should-fix 4* | The "next day" pill (§2) appears the instant the selected offset's resulting clock time rolls past midnight relative to "now," and disappears the instant the user steps back to an hour still on the same calendar day. Purely additive to the existing numeral/tick read — it doesn't change hour-snapping, clamping, or repaint behavior, and it doesn't presume an answer to the bucket-keying question in §8 item 4. |
| **Edge idle (at rest)** — *new, v2* | The idle hint renders on each live edge; no track, no readout, nothing else changes on the map. This is the default state whenever the map is plain (no sheet open) and the edge is live for the current idiom. |
| **Edge mid-drag** — *new, v2* | Same Poka-Yoke posture as the button's mid-drag state: the active track's fill/stop snap to the nearest whole hour continuously, never resting off-hour even transiently. The map repaints on every snap, identically to the button path, because both write the same `selectedHour` (Q3). |
| **Edge unavailable — sheet presented** — *new, v2, Q6* | Touching down on an edge while the heat modal, search sheet, or profile sheet is open does nothing: no track appears, the hour doesn't change, and the idle hint itself is hidden so there's no visible affordance inviting a touch that wouldn't do anything. The heat button is how the hour changes in this state — this is `product`'s call (§5b), not a founder answer, and cheap to overturn if a better interaction answer emerges later. |
| **Edge unavailable — OS-reserved (iPad right edge)** — *new, v2, Q2* | The right edge on iPad never responds to a touch-and-slide, on any screen, sheet or no sheet. A faint neutral ghost mark renders in place of the idle hint so the absence reads as "this edge belongs to the OS here," not as a missed build. |

## 4. Accessibility notes

- **Discrete, announceable steps (PRD req. 6):** VoiceOver's adjustable action on the native `Slider` speaks each new stop as the user swipes up/down — this is a structural property of using `step: 1` on a real `Slider`, not a bolt-on. The control is never continuous-drag-only for VoiceOver users; every step lands on and announces a whole hour, exactly as it does visually for sighted users.
- **Touch target ≥44pt (Fitts's Law, `design-principles.md` §2):** the `Slider` control's own frame — not just its visible thumb graphic — must stay at or above 44pt tall. This is called out explicitly in §2's Hour slider control row so `ios-developer` doesn't ship a visually-slim 28pt track with a matching 28pt tap area.
- **Never color alone (`design-principles.md` §3):** the "now" tick is a distinct shape (a bar, taller than the ordinary per-hour hairlines), and the selected hour is always readable as a printed numeral — meaning is carried by shape and text, with color as a reinforcing (not sole) channel. This directly satisfies PRD req. 5's "meaning is never carried by color alone."
- **Dynamic Type:** the numeral and the "now"/"+12h" end labels use semantic text styles (not fixed point sizes), tested at the largest accessibility sizes — the track and its tick marks are decorative and don't need to reflow with type size, but the numeral's container must not clip or truncate as it grows.
- **Reduce Motion:** the modal's open/close transition, the thumb's snap-to-stop animation, and the near-me/Places-icon fade (§2's chrome-collision fix) all honor Reduce Motion — cross-fade or resolve near-instantly rather than sliding/animating, consistent with T-031's same commitment for its own cold-open title and location marker.
- **Contrast — corrected this pass, REJECT finding 1.** The prior draft asserted 4.5:1 on the end-of-track labels and the "now" tick label without checking the actual rendered color; the mockup was on `--fg-faint`, which computes to **3.22:1 (light) / 3.61:1 (dark)** against the modal surface — both fail, and neither label qualifies as WCAG large text at 9.5–10px. The "day next" flag (§2/§3) was a third instance, at **3.28:1** on its tinted background. **Fixed:** all three now use `--fg-muted`, re-verified against the republished artifact: the numeral, end-of-track labels, and "now"-tick label compute to **6.12:1 (light) / 7.45:1 (dark)** against `--surface` (recomputed directly this pass, §10 — the v1 figure of 6.24:1 light was a close approximation, both clear 4.5:1 regardless); the "next day" pill computes to **~5.09:1 (light) / ~6.01:1 (dark)** against its own `color-mix(--heat 14%, transparent)` tinted background (computed, not assumed, since that background isn't plain `--surface`). All four clear the 4.5:1 normal-text bar (WCAG AA, `design-principles.md` §5) in both themes. The track line and "now" tick (non-text UI) remain at the 3:1 bar, unchanged.
- **Edge gesture is a supplementary path only — v2 addition.** PRD req 6's VoiceOver/Switch-Control bullet is satisfied entirely by the button/modal path, unchanged by this pass: "all 13 hours selectable without performing the edge slide." The edge gesture adds nothing to and removes nothing from that guarantee — it is `aria-hidden`/inert to assistive tech in the mockup, and the TRD should build it the same way (a plain `DragGesture` with no VoiceOver semantics of its own), since narrating a raw pixel-drag control would be actively worse than not exposing it. VoiceOver and Switch Control users reach every hour exactly as they do today, through the button.
- **Edge readout Dynamic Type and contrast — v2 addition.** The floating numeral chip during an active edge drag uses the same semantic text style and the same `fg`-on-`Surface` token pair as the modal's own numeral (17.99:1 light / 14.57:1 dark, §7) — not a new color for the one label that happens to be new. Its container is sized to content, so it does not clip at the largest accessibility sizes, same test as the modal numeral.
- **Edge active-track rail is held to the full 3:1 bar, not exempted — v2 addition.** PRD req 6's inactive-rail exemption is conditional on a *platform-drawn* control (the native horizontal `Slider`); the vertical edge track is custom-drawn (§2), so the exemption does not transfer. Its stop-dot/fill use `fg-muted`/`heat` against `--surface` — 6.12:1 / 7.45:1 and 3.93:1 / 6.62:1 respectively (recomputed §10, the second pair identical to the horizontal thumb's own border-vs-surface citation since it's the same two tokens) — both clear 3:1 in both themes.

## 5a. Q5 — button/modal axis: stays horizontal

**Decision: the heat-button/modal control keeps its delivered horizontal `Slider`, unchanged.** This is designer's call per the PRD (Q5) — not Aviran's, not product's — reasoned here rather than asserted:

1. **The founder's correction was about the edge gesture, not the modal.** Both verbatim quotes ("Supplement (recommended)"; "both edges... you slide the you finger from up to down on one of the edges," `PROGRESS.md` 2026-07-31) describe the *new* entry path. Nothing in either quote touches the already-approved card, and nothing in the PRD's "Not in scope" line (which excludes "the rest of the nav row and its other buttons," not this one) forces a change either.
2. **Form factor mismatch.** The modal is a compact card sized to its content, anchored above the nav row (§2, unchanged architecture). A vertical slider needs a tall, narrow footprint; a horizontal one needs a short, wide one. Forcing a vertical control into a card shaped for a horizontal one either balloons the card's height (crowding the nav row it sits above) or shrinks the usable track well below what req 1's reachability bullet needs. The edge gesture, by contrast, is read directly off the screen's own vertical extent — it has the tall footprint a vertical control actually wants, for free.
3. **Two different physical contexts, not one control wearing two hats.** The edge gesture is a fast, one-handed, glance-free adjustment made mid-map-browse. The modal is a deliberate, both-hands-optional adjustment made with the full readout (numeral, "now" tick, end labels) in view. These are different interaction moments; nothing requires them to share an axis, and PRD req 7's "one direction consistently means later" bullet is scoped to "identically from both edges" — not to the button path, which the PRD's own wording never asks to match.
4. **Changing it would reopen an already-closed contrast question for no PRD-driven reason.** Req 6's inactive-rail 3:1 exemption is conditional on the control staying *platform-drawn* (a native `Slider`). Going vertical means going custom (no native SwiftUI vertical slider exists), which loses that exemption and reopens a contrast bar the current control already clears cleanly (§4, §7). Trading a settled, verified contrast pass for an axis change nothing in the PRD requires is a cost with no corresponding benefit.
5. **Consistent with the additive-pass principle.** `product`'s own record (PRD Technical design, `PROGRESS.md` 2026-07-31) is that this is an additive pass, not a redesign of the approved modal. Keeping the axis is the smallest change consistent with that framing; changing it would be the one part of this pass that isn't additive.

**Consequence for req 1 and req 6 (PRD's own question):** req 1's reachability bullet ("all 13 positions reachable in one continuous edge slide... wherever on the edge the finger lands") binds the **edge path only** — the button/modal's horizontal track was already verified reachable at max Dynamic Type in the v1 pass and needs no re-check. Req 6's rail exemption **survives on the button path** (still platform-drawn) and **does not apply to the edge track** (custom-drawn, held to full 3:1 instead, §4).

## 5b. Q6 — edge gesture unavailable while a sheet is presented: adopted

**Adopting `product`'s call as stated in the PRD, not re-deriving it.** The PRD (Open questions, Q6) records this as `product`'s own working call, made at `architect`'s request, explicitly flagged as "cheap to overturn" — not a founder answer. This spec adopts it as the working assumption for the mockup and the states above (§1.2, §3), for three reasons all already in the PRD's own text and confirmed by this pass's build: (1) Q1's "supplement" answer guarantees the heat button already works in exactly this state, so nothing is lost; (2) an edge drag that outranked a presented sheet's own drag-to-dismiss would make every edge-adjacent drag near an open sheet ambiguous — genuinely worse than losing the edge path for that state; (3) it keeps the TRD's existing D4 guarantee ("the heat modal and a system `.sheet` are never co-presented," which is what makes PRD req 2's "any open sheet is unchanged by an hour change" true structurally rather than behaviorally) intact without reopening it.

**Flagged alternative, not adopted:** a version where the edge gesture *could* coexist with an open sheet (e.g., only the portion of the edge not covered by the sheet stays live) was considered and rejected — it would make the live/dead edge boundary depend on which sheet is open and how tall it is, adding a second per-sheet rule to memorize for a benefit (uninterrupted edge access while, say, `HoodStubSheet` is up) that the button already covers. If a future pass wants this, it should be an explicit product decision, not something this spec back-fills.

## 8. Open items handed to `architect` / `ios-developer`

Not blocking `design-approval`, but real enough to flag rather than silently assume:

1. **The heat modal is a custom overlay anchored above the nav row, not a system `.sheet()`.** This is the single real architectural deviation this spec makes from the obvious default — flagged in detail in §2's Heat modal container row, discovered by building and testing the interactive mockup (an early flush-to-bottom version visually broke the direct-nav-switch requirement). `architect` needs to settle the exact construction: a `ZStack`-layered custom view with its own transition versus some other native-primitive combination — but it cannot be a plain `.sheet(isPresented:)` covering the full screen, or the nav row becomes unreachable while the modal is open.
2. **`selectedHour` write-path onto T-031's `DensityStore`.** T-031 already flagged the read-side seam; this spec is the first writer. `architect` should confirm the binding shape (a plain `@Observable var selectedHour: Int` versus something more elaborate) before `ios-developer` builds both T-032 and the eventual T-034 live-events reader against it.
3. **"Now" re-resolution while foregrounded across an hour boundary — inherited directly from the PRD's own open technical question, not resolved here.** If a user opens the modal at 8:59pm and it's still open at 9:01pm, does "now" silently become the old +0h bucket's neighbor, or does the app need to actively re-anchor? This is a real product/technical call the PRD deliberately left open; this spec doesn't invent an answer, consistent with T-031's own precedent of flagging rather than guessing at build-time performance targets.
4. **Day-boundary hour bucket keying — inherited from the PRD's Open questions & risks.** The mockup's demo deliberately sets its reference clock so +2h crosses midnight, to keep this risk visible rather than accidentally hidden by a benign demo clock — but the actual fix (confirm the data model keys on absolute timestamp, not hour-of-day) is `data-engineer`/`architect` territory, not resolved by this design pass. **Added this pass:** the "next day" pill now in §2/§3 is a display-only readability aid computed purely from the selected offset vs. wall-clock "now" — it renders correctly regardless of how this open question resolves, and does not presume or block a specific answer to the bucket-keying question.
5. **Native `Slider` vs. fully custom control.** This spec's default is a native `Slider(step:)` plus a decorative tick/numeral overlay, specifically because the native control gives VoiceOver's discrete adjustable-action behavior for free (§2, §7). If `ios-developer` finds the native `Slider`'s visual customization too constrained for the "now" tick or per-stop hairlines, a fully custom control is possible — but it must reimplement the same discrete-step VoiceOver semantics manually rather than losing them, since that's a PRD P0 (req. 6), not a nice-to-have.
6. **Edge gesture recognizer construction — new, v2.** The mockup uses pointer events on a fixed-bounds DOM zone; on iOS this is `architect`'s call between a `UIGestureRecognizer` subclass anchored to the edge frame vs. a SwiftUI `DragGesture`/`simultaneousGesture` composition — either way it must (a) live above `Map` in the `ZStack` so it can consume touches before MapKit's own pan gesture claims them (the FB19394663 workaround already in `MapScreen.swift:57-66` is the precedent for "beating MapKit's gesture arbitration," not a new problem), and (b) require a small vertical-dominant initial displacement before claiming the touch, per `architect`'s own recommendation (`PROGRESS.md` 2026-07-31) — cheap insurance against a false-fire from an ordinary horizontal pan that merely starts near an edge.
7. **Exact top/bottom inset values — new, v2.** This spec uses 64pt top / 40pt bottom as the usable-band insets (§2's Edge capture zone row), sized against Notification/Control Center and the home indicator on the devices checked at design time. `architect`/`ios-developer` should confirm these against the actual reserved-zone geometry on a real iOS 26 device rather than take them from this spec as final — the same caveat `architect`'s own feasibility read already flagged for its reserved-zone estimates (`PROGRESS.md` 2026-07-31, "my reading... is the long-standing iOS/iPadOS behaviour; I did not verify against iOS 26's own release notes").

## 9. `ui-design-review` pass — v2, applied not cited

Run against `passenger-brain/design/reference/ui-ux-design-principles-manual.md` and `design/design-principles.md`, on the edge-gesture addition only — v1's own pass (folded into what's now §7's earlier rows) stands unchanged for the button/modal control.

**Passes** — checked against actual numbers, not asserted:
- Capture-zone width (24pt) is stated and justified against a real competing force (MapKit pan arbitration), not picked round. The visible hint (5pt) vs. hit target (24pt) ratio mirrors the already-approved thumb pattern (28pt visible / 44pt frame) rather than inventing a new one.
- Usable vertical band (812pt phone height − 64pt top inset − 40pt bottom inset = 708pt) spaces 13 stops roughly 59pt apart — comfortably clears the 44pt Fitts minimum with margin to spare, checked by arithmetic, not asserted as "should be fine."
- Every new color pairing reuses an existing, already-verified token pair (`fg-muted`/`surface`, `heat`/`surface`, `fg`/`surface`) rather than introducing a new one — closing off the exact failure class L-009's contrast history (Decisions log) was created to catch.
- The rail-exemption conditionality (platform-drawn only) is applied correctly in both directions: kept for the button (still native), removed for the edge track (custom) — not defaulted to "exempt" out of convenience.

**Issues found, and fixed in this same pass:**
- **Found:** the first build of the edge-readout's vertical position used the phone frame's own bounding rect to compute pixel offsets, but the readout element's actual CSS containing block is `#mapArea` (which sits 10pt inset from the phone's outer edge behind its border) — this would have rendered the readout roughly 10px off from the finger on every drag. **Fixed:** switched the calculation to `#mapArea`'s own bounding rect; verified by scripted pointer-event tests in a live browser session (dragging from near the bottom to 30% from the top produced the numerically correct "+8h" with the readout tracking the finger, not offset).
- **Found:** an early version of the "reviewer capture-band overlay" would have sat *inside* the phone frame indistinguishable from shipped chrome, the same class of problem T-032 v1's REJECT finding 4 already fixed for the repaint-timing pill (Artifact conformance rule: a demo/reviewer instrument dressed as app chrome). **Fixed, but not by moving it outside the frame** — unlike the repaint pill (pure text, cleanly relocatable to the rail), this instrument's entire value is showing *where on the actual map* the claimed band sits, which only means anything drawn over the phone. Resolved instead by making it (a) off by default, (b) explicitly toggled from the rail with the label "reviewer instrument, not shipped UI" printed next to the switch, and (c) visually abstract (a translucent tint/hatch, not a labeled pill or button that could be mistaken for a real control) — considered and stated explicitly here rather than silently placed inside the frame and hoped past review.
- **Found, during the Artifact Conformance pass (§10):** the v1 spec's own `--fg-muted`-on-`--surface` contrast citation (6.24:1 light) doesn't match a direct recompute (6.12:1 light). Both clear 4.5:1, so not blocking, but an uncorrected small drift in an already-approved spec is exactly the class of thing the Artifact Conformance rule exists to catch. **Fixed:** every citation of this pair in this document (§1, §4, §6, §7, §10) now reads 6.12:1 light, with the discrepancy stated rather than silently overwritten.

**Quick wins considered, not applied:**
- **A permanent (non-hiding) edge hint, always visible even while a sheet is open or on an OS-reserved edge.** Rejected: an always-visible hint that sometimes does nothing on touch is worse than a hint that disappears exactly when it would lie — Poka-Yoke favors making the invalid state *unreachable* (here: unreachable to notice) over signposting an error after the fact.
- **Haptic-only discovery (no visual hint at all, relying on a first-touch haptic tick to reveal the control).** Rejected: haptics require a touch to already be in progress to fire, so they cannot solve the discoverability problem `product` named — a user still needs a reason to touch the edge in the first place. Visual-first, haptic-as-reinforcement (already the existing P1 haptic-tick treatment) is the right precedence, not haptic-first.
- **Making the edge track match the horizontal Slider's exact visual language (rounded pill fill, identical thumb dot) for maximum path-to-path consistency.** Considered given Q5 keeps the button horizontal, but rejected: the two controls are read in different contexts (compact card vs. full-height edge) and forcing identical geometry would either shrink the edge track's stops below comfortable spacing or bloat the modal's thumb past its settled 28pt — visual consistency here would cost real usability on at least one path for a "looks the same" benefit that matters only to a reviewer flipping between the two, not to a user who only ever sees one path per interaction.
